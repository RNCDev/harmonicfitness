# web/

The web client for HarmonicFitness, called "HarmonicFitness" in the app itself: a FastAPI server (`webapp/`) that runs the engine for a listener from a browser. It is an optional extra; a command-line install doesn't grow.

Install its dependencies:

    uv sync --extra web

On a computer that also has local voices, keep the voice engine's extra too (a sync without it uninstalls PyTorch):

    uv sync --extra cpu --extra web

Run its tests (`./harmonicfitness test` runs them after the engine's, or prints a skip line when the extra isn't installed):

    .venv/bin/python -m unittest discover -s web/webtests -t web -v

Set `HARMONICFITNESS_TEST_DATABASE_URL` (for example `postgresql://postgres@localhost:5432/postgres`) to a Postgres database to enable the database tests; without it they are skipped.

## Admin

People make their own accounts (username and password) while registration is open. Set `HARMONICFITNESS_REGISTRATION=closed` on the web service to stop new accounts; sign-in keeps working. A refused username or password (`POST /api/register`, `POST /api/password`) answers `{"detail": "<why>", "field": "<the box>"}`, the field being `username`, `password`, `current` or `new`, so the page says it under that box. Every refusal has the same shape (0.76.0, `api.error_body`): `detail` as before (the words, or a validation error's list), `code` and `field` at the top when there are any, and beside them `error`: `{"code", "message", "field"}`, the code from the status (`not_found`, `too_many`, `invalid`, ...) or a page's own (`no_model_key`). An error no route caught is a 500 in that shape (`internal`), logged by type and frames, never its message. Ten wrong passwords on a signed-in account in fifteen minutes (changing it, deleting the account) answer 429.

For someone who forgot their password, run from `web/` (or with `web/` on `PYTHONPATH`), with `DATABASE_URL`, `HARMONICFITNESS_BASE_URL` and `HARMONICFITNESS_MASTER_KEY` set:

    python -m webapp.admin reset-password <username>

It clears their password, signs out their devices and prints a one-time sign-in link (24 hours) and nothing else; send it to them yourself. Opening it signs them in, and the app asks for a new password. It never migrates: against a database still missing a migration (one the web service hasn't applied yet) it refuses, exits 1, and says to deploy first.

Where sign-in goes through Clerk (below), the username and password routes are off and none of that applies: a forgotten password is Clerk's to reset.

**The admin screen** (0.87.0; `webapp/books.py`, `webapp/fly.py`, `routes/admin.py`, `client/src/zones/Admin.tsx`, migration 026). The site's books for 7, 30 or 90 days or all time (`GET /api/admin/books?days=`): revenue from minute packs (`sales`, a row per paid pack at what was paid, kept when the account is deleted; a full refund takes its money back once), Stripe's fee (estimated at 2.9% + 30¢), what OpenRouter charged on the hosted site (`costs`, `webapp/costs.py`: a job's writing, every model reply's own charge as OpenRouter reported it, added up by `costs.Metered` around the job's model, the writers' room and the enricher included, and written as the job ends however it ends; a recording's voice at the engine's estimate from builds.jsonl, marked estimated; `provider_spend`, OpenRouter's own daily count for the site's key read every ten minutes, so spend no job claimed shows), Fly (estimated from the machines and volumes running, read with `FLY_API_TOKEN`, a `fly tokens create readonly` token, and priced at Fly's published rates; the shared Postgres cluster, the media bucket and bandwidth are left out and say so), the profit and margin, a day-by-day chart, what a minute sells for and costs to make, how the site is used, and each listener (username and numbers only). A cost that isn't tracked reads "Not tracked" and the profit says it's incomplete, never a silent $0. Only accounts `HARMONICFITNESS_ADMINS` names, by id (a username can be taken again; an entry that isn't an id is ignored and logged), get it; anyone else gets 404, and `GET /api/me` says `admin` so the page offers it. To find an id:

    python -m webapp.admin id <username>

## Sign-in, minutes and the site's own key

The site writes and speaks every workout on a key of its own, and listeners pay by the minute; there are no keys for a listener to add (hosted-only since 0.88.0). Sign-in through Clerk and the minute packs through Stripe are each set up on their own.

**Sign-in through Clerk** (`CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY`, both or neither; `webapp/clerk.py`). `GET /api/auth` then carries the instance's publishable key, and the page shows Clerk's own sign-in form (`client/src/ui/ClerkGate.tsx`, on `@clerk/react`). Once Clerk has a session the page trades its token for this site's own: `POST /api/session` with `{"token"}` checks the token here (its RS256 signature against the instance's public keys, kept an hour; its times; that this instance issued it; that it was made for this site's page, `azp`), then sets the same `wt_session` cookie as before, so nothing else changes for a signed-in listener and no later request calls Clerk. Clerk is asked who the user is only the first time: a Clerk user new here gets an account (a 403 while `HARMONICFITNESS_REGISTRATION=closed`), named after their Clerk username when this site can hold it. The site still stores no email address; Clerk does. `POST /api/register`, `/api/sign-in` and `/api/password` are 404, so there is one way in. Signing out here signs out of Clerk too. Deleting the account asks for a fresh Clerk token in place of the password (`POST /api/account/delete` with `{"token"}`) and deletes the Clerk user first, so a failure there deletes nothing.

Clerk's production instances need a domain of the site's own, so on `harmonicfitness.fly.dev` the instance is a development one (its form carries Clerk's development badge). Moving to a custom domain means a production instance and new keys.

**An account from before Clerk** keeps its files and history when its Clerk user is made with `external_id` set to the account's id (`users.id`): the first sign-in links the two (`auth.for_clerk`, once; an account already linked is never handed to someone else). The id comes from the database, and the user is made with Clerk's CLI or its Backend API (`POST /v1/users` with `username`, `email_address`, `external_id` and a password or `skip_password_requirement`); the person then signs in with that email address or username.

**Minutes** (`webapp/minutes.py`, migration 025). A balance (`users.minutes`, never below zero) and a ledger (`minute_ledger`) written in the same transaction, where (user, kind, ref) is unique, so each thing happens once however often it's asked for.
- **A recording costs its planned length,** rounded up to a whole minute. The Record card says so (`offer.minutes`, and `offer.charge`, what this take takes) and never names dollars or characters.
- **Pressing Record holds them** (`minutes.hold`, ref the turn's job); too few is a 402 with the code `no_minutes`, and the page offers the packs. The hold is kept when the recording's MP3 is stored and handed back when the turn ends without one. A hold whose turn died is handed back by the worker's sweep, ten minutes on at the earliest.
- **The first time a script is recorded again costs nothing** (a fix after hearing it); after that each recording is charged. The ledger knows the script by a keyed digest of its workout folder's name, never the name.
- **Twenty minutes to start with,** once a person: given at the first sign-in whose Clerk email address is verified, and remembered by a digest of that address keyed with the master key (`welcomed`, never the address), so deleting the account and signing up again doesn't give them twice.
- **A workout for later** needs its minutes on hand when it's scheduled and holds them when its turn records.
- **A listener may start forty turns in 24 hours** (`minutes.DAILY_TURNS`), since the site pays for each one's writing.
- `python -m webapp.admin grant <username> <minutes>` adds minutes (a gift, or minutes given back by hand: a part refund in Stripe changes nothing here) and prints the new balance.

**Minute packs through Stripe** (`STRIPE_SECRET_KEY`, or `STRIPE_API_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET`; `webapp/billing.py`, `routes/billing.py`). Three packs (`minutes.PACKS`): 120 minutes for $5, 280 for $10, 640 for $20. `GET /api/minutes` gives the balance, the packs, whether they're on sale here and the last thirty ledger lines in plain words. `POST /api/minutes/checkout` with `{"pack"}` asks Stripe for a Checkout page (the pack's price found by its lookup key, the same as its id) and returns its address; the listener pays on Stripe's page, which sends them back to `/?minutes=bought` or `cancelled`, and no card ever reaches this site. Only Stripe's signed webhook credits a purchase: `POST /api/stripe/webhook`, the one POST with no session and no same-origin check, where the signature (checked against the signing secret, within five minutes) stands in. A paid session credits the pack's minutes from `minutes.PACKS` (never from the request or from Stripe), once per session however often the webhook comes; a fully refunded charge takes back what's left of them. A Checkout session is never asked for twice, and nothing is retried.

Set Stripe up once per account (test or live, whichever the key is), from `web/`:

    python -m webapp.stripe_setup --site https://harmonicfitness.fly.dev --env ../.env

It makes a product and a price for each pack and the webhook endpoint (`checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded`), leaves what's already there alone, and writes a new endpoint's signing secret to the `--env` file as `STRIPE_WEBHOOK_SECRET`, never to the screen. A pack whose price changed in `minutes.PACKS` gets a new price that takes over its lookup key. Each product carries a tax code (`stripe_setup.TAX_CODE`, AI as a service for personal use): Stripe's Managed Payments, on by default on a new account, makes Stripe the merchant of record (it settles sales tax and VAT, and buyers see Link on the page and their statement), and refuses a Checkout page for a product without one.

The live account's server key can be a restricted key with Checkout Sessions: Write and Prices: Read, all the site asks for; the setup itself can run through the Stripe CLI's own session (`stripe login`) instead of a key with more rights.

**The site's own key** (`OPENROUTER_API_KEY`, required: the server won't start without it; `webapp/hosted.py`). The site's own OpenRouter key writes every workout (`google/gemini-3.8-flash`) and speaks it, and listeners pay in minutes. That key goes only to the worker's model client and, under its variable name, to the engine for a job; no route returns it or its balance, and the engine's output is scrubbed of it. Keys listeners stored before 0.88.0 were deleted with the `user_keys` table (migration 027).
- **The coaches that speak here** are the shipped OpenRouter coaches on `google/gemini-3.8-flash-lite-tts` (`hosted.speaks`, since 0.85.1: Ben, Cole, Dev, Drew, Hank and Paul; Ana, Elise, Jo, Lena, Ruth and Zoe). The packs were priced against MAI-Voice ($22 per million characters, about 1.4 cents for a minute of a workout); Gemini Flash Lite is billed by the audio it makes, about $14 per million characters or 0.9 of a cent a minute, so a minute sold earns more than before. A coach on a dearer model would cost the site more than a minute sells for, so `/api/start` and the Coaches page list only those, a coach chosen before that isn't one is replaced by the first of them for the turn, and a build priced on any other service or model is refused before it records.
- **Changing what a minute costs the site** (another voice model) means `hosted.VOICE_MODEL` and a look at `minutes.PACKS` together.

## The engine on the web

Every job runs the engine with `HARMONICFITNESS_WEB=1`: no local voices, a stock web coach by default, and the finished MP3 is kept for the app to upload.

## Agent

The app is a chat, a Settings drawer (tabs for the listener's minutes, their level, Record without asking, their private podcast link, the background and their files, one shown at a time, with their account always at its foot) and the Coaches and Logs pages. The level is picked from three cards, each a short name over the sentence that fits them (`GET` and `PUT /api/level`, `webapp/level.py`; `GET` reads only the profile's four files): novice until one is chosen, as the engine plans, and saved with the engine's `set experience`, every other line of the profile kept. The coach works as Claude Code does on a listener's computer: one agent (Pydantic AI) follows the workout skill itself (`.claude/skills/workout/SKILL.md`, read from the engine at run time; `research.md` is for a computer's research agents, so it isn't given) under a short preamble (`webapp/agent/instructions.md`) that says what the web client offers in place of each Claude Code tool, as `AGENTS.md` does for Codex. Questions are asked in the chat and research is done in turn. A new listener (no experience level in their profile yet), or one who asks to be set up, also gets the setup skill: its quick start in the chat, a coach chosen on the Coaches page, then a ten-minute first workout. The check-in may change `health.md`, with the listener's permission, as the skill says. Once a turn has read text strangers wrote (a web search, the feeds, a fetched page, the research folder), no limit may be loosened there that turn (`tools.loosened`: a limit lifted or cleared, off-limits eased to delicate, a clinician's rule dropped), and a scheduled workout's turn never changes it (0.76.0). On the worker, feeds and topics fetch only public addresses, youtube only YouTube's, and none of them gets the site's key.

**Recording costs money, so it waits for the listener.** A full build is first only priced: the `run` tool lints the draft (skipped when the same text just linted clean with the same coach), takes the character count the lint prints for a web voice and prices it (`get cost`), and keeps the offer in the conversation; the chat shows a Record button with the price, on a card that also shows the plan, worked out by the engine from the draft's own segments (`get plan --draft`, read beside the price, so its times always add up) and, before the first build that sends a script to a voice service (`get web-builds` is 0), where the script goes and what that means (the privacy line), so the model writes neither. With **Record without asking** on in Settings (`users.auto_record`, migration 014, off by default; `PUT /api/auto-record` with `{"on": true | false}`, returned by `GET /api/me`), a clean price records at once in the same turn: the worker reserves the characters from today's allowance as the Record endpoint does, and past the allowance the offer stays and the Record button says why. `POST /api/conversations/{id}/record` reserves those characters from today's allowance (`spend`, `HARMONICFITNESS_DAILY_CHARS`, default 180,000 a day) and queues a turn in which the same build runs, with `--max-chars` set to the approved count. That turn loads the listener's kept clips (`clip_cache`, sealed, a week), so a re-record sends only lines that changed, and keeps the new ones. A clip is marked used only when a build read it (the engine touches each one it uses), without being sent again; past 400 MB the clips used longest ago make room (0.76.0). The worker keeps each MP3 the turn made (`media`, sealed with the user's data key) and adds it to the chat as a player with a download: a workout's until the listener has three newer ones (making a fourth deletes the oldest, migration 017), any other for 24 hours. `GET /api/media/{id}` serves it to its owner only (byte ranges for Safari; `?download=1` for a download; `Cache-Control: private`), a conversation marks a recording no longer kept `gone` so the page says so, and the worker deletes MP3s past their time and week-old clips. MP3s never go into the store, except a coach's sample (`coaches/<slug>/sample.mp3`, `folder.COACH_SAMPLE`), which the Coaches page plays through `GET /api/coaches/{slug}/sample.mp3`: the listener's own copy first, else the one the engine ships. With three writers, a turn whose price is in (and its log kept) ends there in code, with no model request: `run_turn` runs the agent with `AGENT.iter` on a loop of its own and stops before the next request, saving the coach's closing line (`agent.closing_reply`: ready, longer than a scheduled ceiling, or today's allowance used up) as the reply. One approval records once: the approved build spends it, and once it has made an MP3 (exit 0, or 2 when the total ran a little off plan) the workout is final for the turn (another build or a rewrite of its draft is refused). As soon as it has, the worker keeps what it made (the files written back, a coach designed for it among them, the clips and the MP3), so a turn that then stops or fails loses none of it, and the failed conversation still shows the audio. Each kept MP3 names the build that made it (`media.build_id`, from the build record beside it), and `GET /api/workouts` adds a logged workout's MP3 while it's kept (the three newest), which the Logs page plays.

**The private podcast feed.** Settings' **Podcast** tab makes a link a podcast app follows (`POST /api/feed`; `GET` shows it again, `DELETE` turns it off), so each new workout lands on the listener's phone by itself, downloaded for offline play. A podcast app can't sign in, so the link's token is the key: 32 random bytes, of which only the sha256 finds the user (`users.feed_hash`, migration 018), with the token sealed under the user's data key (`users.feed_token`) so Settings can show it again. `GET /feed/<token>.xml` (`webapp/feed.py`) lists the workout MP3s the site keeps (the three newest, so the app has each before it goes) as RSS with the iTunes tags, blocked from directories (`itunes:block`) and its artwork `podcast-cover.png` (from `assets/brand/make.py`); `GET /feed/<token>/<id>.mp3` serves one, byte ranges and all, and never a coach's sample. A new link stops the old one, as turning it off does; an unknown token is a 404, like a workout no longer kept. Settings says plainly that anyone with the link can hear the workouts.

**Ready-made workouts.** Five thirty-minute workouts recorded once (`./harmonicfitness ready`, `docs/demos/ready.toml`), listed from `client/src/ready.json` (written by `ready upload`) by `zones/Ready.tsx`: on the sign-in page beside the demo clips, as their own panel, with no account needed; on the welcome card before any key; and on a new listener's first screen. They play straight from the public media bucket, and the list says they aren't adapted to any injury. Until the set is uploaded the list is empty and shows nothing.

**The plan while the words are written.** When a skeleton lints clean and the writers' room starts filling it (a minute to three), `tools.show_plan` runs `get plan --draft` on the skeleton and sends the plan as a `plan` job event; the chat shows it under the coach's steps until the Record card shows it again with the price.

**A workout for later** (0.60.0). The page's sentence ends ", right now" or a time the listener picks, every half hour for the next day ("at 7:00 PM", "tomorrow at 6:30 AM"); with a time, `POST /api/conversations` carries `start_at` (ISO with the browser's offset), and the conversation keeps it as `later` (a time inside fifteen minutes runs at once; one past a day is refused). The first turn is the check-in only: the worker tells the agent the time, `brief` is refused until the later turn, and once nothing's left to ask the agent calls `schedule_workout` (offered only then), which prices the session's minutes with the coach (`get cost` at 650 characters a minute for the estimate and 800 for the ceiling, as priced scripts run) and ends the turn. The chat shows the estimate, the ceiling and **Schedule it**: that press is the one approval. `POST /api/conversations/{id}/schedule` queues a `turn` job with `jobs.not_before` fifteen minutes before the time (migration 016; `jobs.claim` skips a job until it's due, and a job not yet due doesn't count toward the queued cap) and moves the conversation to `scheduled`, where it takes no messages. When the job is claimed the worker wakes the conversation (`conversations.wake`: only for that job, so a cancel that raced the claim leaves it alone), sets the listener's date and time from their offset as it is then, and runs the turn with Record without asking on and the ceiling as its limit: a clean price under the ceiling records at once, within today's allowance; one over it waits with the Record button and its real price. `POST /api/conversations/{id}/cancel` fails the queued job ("cancelled") and puts the conversation back to idle with its plan kept; once the turn has begun, Stop ends it. The page reads a scheduled conversation every 30 seconds to see its writing begin, and the worker logs how long after its due time each scheduled turn began.

**Stop.** `POST /api/conversations/{id}/stop` flags the running job; the heartbeat looks every two seconds and sets the job's cancel event, which cancels the model run and kills the engine's process group (`engine.run(cancel=)`), so nothing keeps billing. The conversation says "Stopped." A deploy stops the worker with SIGTERM: it finishes the job it's running, and one still running four minutes on (`worker.DRAIN_SECONDS`, inside `fly.toml`'s five-minute `kill_timeout`) is stopped the same way, saying the site restarted. The heartbeat tries again on a new connection when one fails (three tries, inside reap's two minutes); a job it loses is stopped too, so nothing more is spent on it.

**Kit photos** (0.83.0). The camera button beside the message box adds up to three photos of where the listener trains (`client/src/lib/photos.ts` draws each again at 1600 pixels at most and sends a plain JPEG, so its metadata, where it was taken among it, stays on the phone). `POST /api/conversations` and `.../messages` take them as `photos` (base64; the body limit grows for those two paths only, `api._BodyLimit.PATTERNS`), and `webapp/photos.py` re-saves each again with Pillow (upright, a plain JPEG, nothing carried over), refusing anything but a JPEG, PNG or WebP. They wait in `turn_photos` (migration 024), sealed with the user's key and tied to the turn's job, never in its args: the job holds only how many (`turns.request` checks it), and the chat line shows that count, never a photo. The worker reads and deletes them in one statement as the turn begins (`photos.take`) and gives them to the model with the line (`agent.with_photos`); the saved history holds a line in their place (`agent.without_photos`), so neither the conversation, `pull` nor a later turn has them, and the retention sweep deletes any no turn took within the hour. The agent reads the kit from them by the setup skill's Kits from photos, which every web turn carries (`agent.kits_from_photos`), and reads it back before writing anything. A workout for later takes none: its turn runs after they'd be swept. The photos go to the listener's own model provider to be read, as the box says.

**When the database drops a connection** (0.76.0). Job events go on a connection of their own (autocommit), so a progress line never commits or rolls back the job's work. What a recording made (its files, clips and MP3) is saved again on a fresh connection when the first was dropped (`Ctx.retrying`), and the job is finished on one that works, never left for reap. Each lane opens its connection again between jobs once it's twenty minutes old. Every lane restarts after an unexpected error, and every failure line carries the frames it passed through (`webapp/log.py`), never the exception's message. Once a minute the quick lane (0.77.0; the main lane before) sweeps expired MP3s, week-old clips and (`webapp/retention.py`) finished jobs fourteen days on (a conversation's own job is kept), expired sessions and links, and allowance days over thirty days old; conversations stay, since `pull` can fetch any of them.

**Logs.** The Logs button beside the gear opens a page of the listener's logged workouts (the chat stays as it was, behind it): each one's date, length, format, kit, coach, movements, topics and feedback, its script on request, a rating (positive, neutral or negative; pressing it again clears it), a line of feedback, and delete (after a confirm), with search, filters (rating, format, kit) and sorting in the page. `webapp/workouts.py` runs the engine's `workouts` command on the listener's files in a temporary folder, as `/api/start` does: `GET /api/workouts`, `GET /api/workouts/{ref}/script`, `POST /api/workouts/{ref}/feedback`, `PUT /api/workouts/{ref}/rating` and `DELETE /api/workouts/{ref}` (its folder and files too), where `ref` is the build id, or the workout's number when it has none. A change is written back against the versions read; a turn saving at the same moment makes it a 409, to try again.

**Learning from feedback.** A feedback line saved on the Logs page (`POST /api/workouts/{ref}/feedback`, now 202 with `{"job_id"}`) queues an `enrich` job, which runs in a lane of its own (migration 015: `one_running_job_per_user` now leaves enrich jobs out, and `one_running_enrich_per_user` keeps those to one a user; the worker runs a second loop, `serve(lane="enrich")`, beside the main one), so it never waits behind or blocks a workout. It runs `./harmonicfitness workouts context <ref>`, makes one structured request on the site's own key (`webapp/agent/enrich.py`: up to twelve signals and a summary, with the writer's web search to pin down a name; the shape has no field for health), applies the signals with `interests add --source feedback`, and saves the files at once; when a turn saved the evidence file at the same moment, it applies them again on the files as they stand, without a second model call. The Logs page follows the job (`GET /api/jobs/{id}`) and shows its summary under the workout. A rating needs no model: the engine's `workouts rate` writes its signals itself. "Tell me what you enjoyed" on the first screen fills in "Lately I enjoyed " for the listener to finish; the turn treats it as one job (`agent.ENJOYED` keeps "I enjoyed a 5k run" from reading as a workout request), records it with `interests add --source mention`, and says what it picked up.

**Syncing with a computer.** `./harmonicfitness sync` signs in as the listener and keeps their computer's `me/` in step: `GET /api/sync` lists each file the site keeps (path, version, sha256), `POST /api/sync/read` returns bodies (base64), and `POST /api/sync/write` applies each change through `store.write_back` over the version the computer last saw, so a file a turn saved since is a conflict, left as it is. Paths the site never keeps (`folder.SKIP`, but each coach's `sample.mp3`) and auditions are refused.

**Leaving.** `GET /api/export` is every file as a ZIP laid out as `me/` (keys are never files here). `POST /api/account/delete`, with the password (or a fresh Clerk token, where sign-in goes through Clerk), deletes the user row and everything that hangs from it, any minutes left among it.

Its seven tools (`webapp/agent/tools.py`, and `write_script` and `schedule_workout` in `webapp/agent/__init__.py`):
- `run`: one `./harmonicfitness` command in the listener's folder (five minutes; a full build gets the workout's own length, at least ten, and the turn's clock waits for it). Allowed: brief, build (not `--follow` or `--clips-only`), check, content, coaches (list, last, measured, make, forget-audition, archive; never `audition` or `keep`), coverage, feeds, get, help, interests, keys, log-session, movements, topics, workouts, youtube. A voice design (`coaches make`) gets 10 minutes. `me/...` paths in arguments become the folder's own; any other path is refused.
- `read_file`: `me/...` (never `me/.env`) and the engine's `knowledge/`, `.claude/skills/` and `coaches/`.
- `write_file`: `me/...` only; never `me/.env`, the kinds of file the store doesn't keep, or an audition's own files (only its narrative, `me/coaches/.auditions/<slug>.md`).
- `edit_segments`: segments of a draft by their places (the lint's # column), each the whole new segment with its `@@` line first, all in one call and all or nothing: a lint's fixes go in one request, not the whole script again and not one segment a request. Refused once the draft is recorded. It and `write_file` say what a draft's segments add up to, so a length that misses the request is caught before the lint.
- `list_files`: under `me/`.
- `schedule_workout`: prices a workout for later and ends the turn (A workout for later, above); offered only then.
- `write_script`: fills a skeleton with the script's words (the draft's path, `build_name` and `coach`), then builds it, as `write_file` does. A clean skeleton no longer needs it (it goes straight to the writers' room, below); it stays for a skeleton written before. It runs the writers' room (`webapp/agent/writers.py`), the site's default; `HARMONICFITNESS_WRITERS=one` takes the tool away, and the agent writes the words itself in passes with `edit_segments`.

**The writers' room.** The agent plans the session and writes the skeleton with `write_file`: every segment's seconds, counts, holds and `[reps N]`, each set's dose and weight in its label, each rest a segment of its own labelled just `Rest` (or `Transition`: never a topic or a movement's name), and an empty `[story] [/story]` after the go of each steady timed set that will carry a story. A skeleton within ten percent of the request is settled by the site, the difference spread over its rests (`tools.settle_clock`). Its lint gives each segment's word budget, and once that lint is clean the same `write_file` (or the `edit_segments` that fixed it) hands the words to the room at once, with no model request between (`agent._chain`). Four writers, each a model call on the listener's writer key, each given only its own task (`researcher.md`, `trainer.md`, `host.md`, `review.md` beside it) and its own parts of `knowledge/script.md` and `knowledge/tts-rules.md`:
- **The researcher** starts as soon as the brief is saved (`brief --save`), while the agent plans the skeleton. From the listener's topics, the content plan, the stock, today's sheets and its own web searches, it returns each story as notes (why it's theirs, the facts, the point), marked for steady work or a rest. A story the plan lists as told before is dropped for a spare, and asked for again only when too few would be left. It writes before the skeleton exists, so when the skeleton has more places than it wrote for, it's asked for the rest while the trainer works (`writers.top_up`), going on from its own run.
- **The trainer**, at the same time, turns the brief and the movements' coaching notes into notes for each segment, sized to the words the plan gives it (and, where a story goes, the words left for the coaching around it), with the safety points as plain notes: no label in front of one, so nothing meant for the host can be read aloud.
- **The host**, the coach's voice, writes every segment from both, to about its budget, as one person talking. Code places the stories: each rest, and each marked steady set, takes the next story that suits it, and the spares go when there are fewer places. A story gets about 70 percent of a rest's words and 55 percent of a steady set's, but always leaves the coaching at least 60 (`writers.COACHING_FLOOR`), what a breath, a self-check and what's next take; the host is told both shares. A rest left without a story is told so, and that its label is no story to tell; a story the host tells there anyway is taken out before the review, which fills its time with coaching (`writers.without_unasked`). A fixed hold or pause over eight seconds is taken out, and the coach talks through those seconds instead.
- **The trainer's review** checks what matters to the body (the opening's rules and that an AI wrote it, each limit's side, its one reminder) and the build's check (`--lint-only`), fixing only what fails and leaving the host's voice alone. Each of its edits is checked again, and it goes round again while the check still finds something, up to three rounds (`writers.REVIEWS`): the room never hands back an edit nobody checked. A clean lint here is remembered, so the build after the room prices the same text without linting it again.

The researcher and the review think at LOW, the trainer and the host at MEDIUM (`writers.LEVEL`): at MEDIUM the researcher took 78 to 160 s and held the room up for most of that, at LOW 17 to 27 s. A writer that runs past its patience (`writers.PATIENCE`), or is cut off by Gemini's own deadline, is asked again thinking less. When the room is done, the draft builds and prices as any other, and the agent fixes what's left with one `edit_segments`. The worker's log has a `room` line for each writer (its level, seconds, tokens and searches, and whether it was asked again), each lint, how long the room waited for the researcher, and the room's whole time: never what any of them read or wrote.

**The bench.** `web/bench/` times the room from the brief to the price on the maintainer's own key and reads the scripts for what matters to the listener; its README has the method, the rule for keeping a change, and every result so far.

**Web search.** The writer has OpenRouter's web search (`agent.SEARCH`, pydantic-ai's `WebSearchTool` as a run capability, low context, at most eight a turn), billed on the site's key. In the writers' room only the researcher searches (the agent is told not to): about six a workout, for the topics due the feeds don't cover, what's on at their venues and near them, and quick hits for the work, and only a source from the past two weeks makes something news. With `HARMONICFITNESS_WRITERS=one` the agent runs the same six itself, after the check-in. The turn's log line counts them, the room's included.

**Logging, after the recording.** Once a recording is made, the site logs it itself, so the model spends no request on each: the stories the writers' room told (`content log`, from the room's own list), and the session's `log-session`. With three writers, the agent hands over the log's fields with the skeleton's `write_file` (`log`: format, topics, loads; `tools.log_argv`), so code keeps the log and the agent sends no `log-session`; a later turn that revises the same draft keeps it (`agent.carry_log`). Otherwise the agent sends `log-session` ahead of the recording. A `log-session` for a draft not recorded yet is kept ("Kept", a success on the listener's steps as "Noting the session for your log") and run the moment the recording is made; both ride on the offer, so a Record button's turn has them. Either one refused goes back to the model in the recording's result, to fix and run itself.

**Topics, quickly** (0.63.0). The page's "I'd like to update my interests." (or "add a topic", with nothing named) is answered at once by the worker, with no model request: "What's on your mind? ... Or do you want me to offer some trending topics?" (`agent.TOPICS_OPENER`), kept in the history as the model's reply. A topics job (`agent.topics_job`: asked for now, or the conversation began with it, and the line asks for no workout) is a light turn: no workout skill or writing guides, no web search, no background `feeds`, and in place of step 1 only content.md's topics, venues and never-bring-up lines. The agent adds what they name with `topics add`, whose `--feed` finds a site's, newsletter's or podcast's feed itself; trending ideas come from `content trending`. A workout asked for after the opener reads step 1 as a first turn would.

To save round trips, the worker does three things itself. The instructions carry `knowledge/script.md` and `knowledge/tts-rules.md` after the skill, so the model never reads them. With the writers' room, `script.md` stops before its craft ("Getting the workout done" on), which the writers read instead. On a conversation's first turn it runs step 1 of the skill before the first model request, all at once (`check`, `content plan` for the length the request names (else 25), `get coach`, the coach's `get route`, `coaches list`, `get web-builds`, today's workout folders, and reads of `profile.md`, `training.md`, `health.md` and `log.md`), and hands the results to the model with the listener's first message. It starts `feeds` in the background as a turn begins, once the check-in is answered (each later turn, or a set-up listener's first turn when it asks for a workout, which the page's sentence answers), unless today's sheet is already there; a `feeds` run in the turn (the writers' room's, or with `HARMONICFITNESS_WRITERS=one` the model's) waits for that run instead of starting another, and the turn ends only once it has finished. In the writers' room the agent itself doesn't run `feeds`: the researcher reads the sheet and the host gets the weather.

**The worker's log** has a line for each step of a turn with how long it took (`run build --lint-only exit 1 4.8s`, `think 76.1s` for a model request, `edit_segments exit 0 0.0s`) and one for the whole turn (its seconds, model requests and tokens in and out): never what was read, written or said. `./harmonicfitness pull` saves the model's side of the latest conversation as `history.json`, for the listener's own look at what each step did.

**A coach of their own** is made on a computer, not here. On the site a listener picks from the stock web coaches on the **Coaches** page, and the agent points them there when they ask for a new coach or a different voice. `coaches audition` and `coaches keep` are refused. A coach they made before stays theirs, and an audition left open from before is closed with `coaches forget-audition`, which deletes Gemini's unkept voices.

Safety is the engine's: the brief's safe menu and the build's menu gate (movements off the menu, one side only, names the catalog doesn't hold) refuse what the writer gets wrong, as does its check that a one-sided limit's side is named in the opening.

A conversation is a series of short `turn` jobs. Each runs one turn in the listener's temporary folder, written on the site's own key, then saves the conversation (its history and chat lines) sealed with their data key, and writes back the files its folder changed (`health.md` only as above). The model history it saves drops each request's instructions (each run sends its own), and past 400,000 characters an earlier turn's long tool results are shortened to a line (`agent.compact`). A turn stops at 60 model requests, 120 tool calls, 3,000,000 tokens or fifteen minutes (longer while a recording runs); nothing is retried (`max_retries=0`, 180 seconds per request).

The site writes with OpenRouter (`google/gemini-3.8-flash`, on the same key as its voices, at the same thinking levels as Gemini, as OpenRouter's reasoning effort; `webapp/providers.py`). Claude, ChatGPT and Gemini's own API are kept there for the bench (`web/bench/`), not offered to listeners.

While a turn runs, the chat shows each step in plain words ("Checking today's safety limits", "Recording your workout"), never a command or a file's name, and, while the model itself works between steps, a live line saying what it's thinking about ("Reading your message", "Writing your script"), which goes once it's done. A step running longer than eight seconds shows its own clock, and past 25 seconds a line says why it's a long one. A listener not set up yet who asks for a new coach gets the coach first; setup waits until it's made.

The model provider sees the files the agent reads (the profile, health and log among them), the engine's output, the skill, the chat, and the local date and time.

The page opens fresh: a finished conversation isn't shown again. It opens on one that isn't done: one still working, which it follows (a reload in the middle of a turn keeps its steps and Stop), or one from today waiting on the listener (the coach spoke last, or a Record offer is open), as long as it hasn't failed or recorded a workout yet. "New workout" clears the page; the next message starts a new conversation, as does a message after a conversation from an earlier day.

**Before signing in.** The sign-in page opens on its front (`client/src/zones/SignIn.tsx`): Sign in and Make an account in the header, what seven invented listeners asked for on the left (`client/src/zones/Demos.tsx`), and the free ready-made workouts on the right. Someone who has signed in on that browser before opens on the form instead. Each demo reads as the request the app would send for them ("Hey, coach Priya, I'd like a 30-minute full-body workout in a hotel room, right now. Go easy on my left knee today."), with who asked, what changed for an injury, and two minutes of the workout it made to play from the media bucket; the seven names under the player pick another. `client/src/demos.json` is written by `./harmonicfitness demos web` from `docs/demos/demos.toml`; nothing is asked of the server.

**The first screen.** `GET /api/start` gives what the page's opening sentence is filled in with ("Hey, coach Reed, I'd like a 25-minute strength workout at home. Go easy on my left knee today."; each blank opens its choices, and the second line opens a body chart: areas head to feet, each side a three-way toggle tapped from OK to "go easy" to "keep off"): the coaches that speak on the site (`hosted.coaches`), each ready, the one used last (else the first) first and marked current; the profile's kits, then the engine's presets, each with words for "at ..." ("a hotel room"); the usual length from the profile's Default session (10 to 60, else 25; ten for a new listener with no level yet, the quick start's first workout); `health.md`'s limits; a suggestion from `coverage` (a body part not trained this week, or the days since the last session; null with nothing to say); and whether setup is still quick. It writes the listener's files to a temporary folder and runs `coaches list --json` and `coverage --json` there, side by side; it changes nothing. The answer is kept in the web process per listener (`start.cached`, an hour at most) under what it was made from: the files' versions (`store.fingerprint`, read from the rows without opening a path or body), the chosen coach and the day; any change to one makes a fresh answer, and signing out or deleting the account drops it. The page shows the sentence at once, its blanks rolling in when the answer comes. The sentence goes as the first message, and the agent takes its answers as the check-in's (`agent/instructions.md`); a limit from `health.md` can be tightened there for the day, never loosened. A new listener (no level yet, `"new": true`) answers the quick start's first questions above the sentence, in one go: what to call them, which of the three levels sounds like them, and what they have at home, with a note that the first workout records as soon as it's written, and where its script goes (the privacy line). The answers go after the request as one line ("About me: call me Sam. I'm new to this, or it's been a long while. At home I have ..."), which the agent takes as the round answered, asking none of it; and that conversation's first recording runs with no Record card (`agent.about_me`, in the worker's turn), within today's allowance, as Record without asking does. Below it, "Or ask for something else" lists the other common asks, each with a line saying what it does (an injury, equipment, what fills the rests, a coach, feedback).

**The look.** Moonrise, after Ansel Adams' "Moonrise, Hernandez": dark only, with a faint moving pattern behind every page (`client/src/ui/Sky.tsx`), the listener's choice in Settings (`ui/Sky.tsx`'s `SKIES`, painted by `lib/skyPaint.ts`): Flow (fine lines drifting sideways, an SVG translated in a loop), Field (a grid of dots on a canvas, crossed by a ripple from the top right every seven seconds), Waves, Bloom, Woven Grid or Node Garden. All hold still under the system's reduced-motion setting and brighten a little while the coach works. The choice is saved per account (`users.sky`, migration 011, null meaning Flow): `GET /api/me` returns it as `sky`, and `PUT /api/sky` with `{"sky": "flow" | "field" | "waves" | "bloom" | "woven" | "garden"}` sets it (anything else is 422; `keystore.SKIES`). Big Shoulders Display for headings, the request and buttons; IBM Plex Sans Condensed for the rest; the logo's coral for the request's fixed words and, in Settings, a small mark on what's chosen (the `--accent` role), cream for everything you act on.

Routes: `GET /api/me`, `PUT /api/sky`, `PUT /api/auto-record`, `PUT /api/coach` (`{"slug", "day"}`: the coach chosen in Settings or the sentence, kept in `users.coach` and `coach_day`, migration 012, as the first screen's coach and the chat's until a workout logged on a later day used another), `GET /api/start`, `POST /api/conversations`, `GET /api/conversations/latest`, `GET /api/conversations/{id}`, `GET /api/conversations/{id}/history` (the model's side, its owner only, for `./harmonicfitness pull`; the page never shows it), `POST /api/conversations/{id}/messages`, `.../record`, `.../schedule`, `.../cancel` and `.../stop`; `GET /api/media/{id}`; `PUT /api/writer`; the level, keys, balances, jobs (`GET /api/jobs/{id}` and its `/events`), workouts and coach sample routes above; `POST /api/import`, `GET /api/export`, `GET /api/sync`, `POST /api/sync/read` and `/write`, `POST /api/account/delete`; and, above, `POST /api/session`, `GET /api/minutes`, `POST /api/minutes/checkout` and `POST /api/stripe/webhook`.

## Run it locally

With Postgres running and the web extra installed (`uv sync --extra web`), one command runs the server and the worker together in one terminal, each line labeled `[web]` or `[worker]`; Ctrl-C stops both:

    web/dev.sh          # builds the client, then serves it at http://localhost:8000
    web/dev.sh hot      # adds Vite at http://localhost:5173, which reloads as you edit the client
    web/dev.sh reset    # deletes the local database and key, for a fresh start

It makes the database `harmonicfitness_dev` (`HARMONICFITNESS_DEV_DB` changes it) and a master key in `.cache/webdev/` (git-ignored) the first time, and keeps both between runs. The site's own keys (`OPENROUTER_API_KEY`, which it needs, and Clerk's and Stripe's test keys, which it doesn't) are read by name from the repo's `.env` when it's there (git-ignored, never printed); what your shell sets wins. A Stripe webhook can't reach `localhost`: `stripe listen --forward-to localhost:8000/api/stripe/webhook` forwards them, with the signing secret it prints as `STRIPE_WEBHOOK_SECRET`.

## Serve

Run from `web/`, with `DATABASE_URL`, `HARMONICFITNESS_BASE_URL` and `HARMONICFITNESS_MASTER_KEY` set (the same as the admin commands). It applies any database migrations once at startup, then serves the API and, when `web/client/dist` has been built, the client:

    uvicorn webapp.api:create_app_from_env --factory --no-access-log --host 0.0.0.0 --port 8000

`--no-access-log` matters: a one-time sign-in link's page is `GET /link/<token>`, so an access log would write those tokens to the logs. The server itself logs no token, job argument, event or result.

The session cookie is `Secure` unless `HARMONICFITNESS_BASE_URL` starts with `http://localhost` or `http://127.0.0.1`, so local development works over plain http. Every POST must carry an `Origin` (or `Referer`) of `HARMONICFITNESS_BASE_URL`'s origin, so set it to the address the browser uses. No request body over its route's limit is read (`api._BodyLimit`, 0.76.0): 64 KB, but 10 MB for an import, a sync's 30 MB in base64 and 512 KB for a sync's read. Over https every response carries `Strict-Transport-Security`.

**How the server is laid out** (0.76.1). `webapp/api.py` builds the app: its middleware (`api._BodyLimit` among them), its one shape of refusal (`api.error_body`) and its connections. The routes are in `webapp/routes/`, a router per area (`auth`, `account`, `files`, `logs`, `media`, `settings`, `jobs`, `conversations`, and `client`'s catch-all last), included in the order they're matched. `routes/state.py` holds what they share: the app's state, the session and same-origin dependencies, and the two ways a route holds a transaction, `tx` (commits on the way out) and `read` (never does); either rolls back on any raise, a refusal too. No function that reads or writes data commits or rolls back: its caller does, a route through `tx` or `read`, the worker loop for its jobs; only the job queue's single-step units of work, the sweeps and the migrations commit their own (`test_wiring` holds that). The web process never imports the worker: what both use is in `webapp/enginelib.py` (the engine's modules, imported with no `me/` in reach) and `webapp/turns.py` (a turn's arguments, checked). `HARMONICFITNESS_DAILY_CHARS` and `HARMONICFITNESS_WRITERS` are read once, at start (`config.Settings`).

**Room to grow** (0.77.0). What a request costs no longer grows with the number of listeners or the length of their history:
- **Progress streams share one listener** (`webapp/streams.py`): one thread holds one connection that LISTENs on `job_events` and wakes the streams following the job each NOTIFY names. A stream holds no connection or thread of its own; it reads its job through the pool in short calls, and its status read every five seconds covers a NOTIFY sent while the listener was reconnecting. The thread starts with the first stream and stops with the last. A listener may have three streams open; a fourth ends their oldest, which the browser opens again from its last event.
- **Requests read only the files they need** (`store.read_many`, `read_where`, `digests`): `/api/sync` lists each file's SHA-256 from a sealed digest (migration 021, filled on every write; a file written before is hashed from its body), `/api/sync/read` opens only the named files, and the Logs calls leave out the coaches and the research stock, which the engine's `workouts` command never reads. The workout list is kept per listener until a file changes, as the first screen's is.
- **MP3s are kept in sealed 1 MB chunks** (`media_chunks`, migration 022): a player's byte range opens only the chunks it covers, and the answer streams a chunk at a time, each read on a pooled connection of its own. An MP3 kept whole before is read as before until newer ones replace it.
- **The worker runs two turns at once** (`HARMONICFITNESS_WORKER_SLOTS`, 1 to 4, default 2), a balance check in a lane of its own (`quick`, migration 023), never behind a turn, and enrichment in its own, as before. One recording renders at a time in a worker (`agent.tools.RECORDING`; a turn waiting for one keeps its clock and its Stop), and step one's engine commands run at most three at once across its turns. `HARMONICFITNESS_WORKER_SLOTS=1` runs one turn at a time, as before.

## Client

The browser client is in `client/` (Vite, React and TypeScript; Node 20 or later). From `web/client`:

    npm ci
    npm test          # the client's own tests
    npm run build     # writes dist/, which the server above serves
    npm run dev       # a dev server on :5173 that sends /api and /link to the server on :8000

How `client/src/` is laid out:

- **`tokens.css`**: every colour, tint, size, space, corner, line (a geometry, `--ring`, `--line-*`, `--mark-*`, that a rule gives a colour), weight, line height, opacity, focus ring, layer, duration and a phone's safe edges (`--safe-*`), the one list, with the four breakpoints in its header. Its palette (`--ink`, `--sheet`, `--stop`…) is what the roles are made of; the stylesheets use only the roles (`--text`, `--text-muted`, `--surface`, `--border`, `--action`, `--danger`, `--sample`…), so a second theme would redefine the roles alone. `docs/tokens.css` is an exact copy and the web player page (`tools/webcopy.py`) inlines it (`tests/test_tokens.py`).
- **`theme.css`** is only the list of the stylesheet's parts, in cascade order: `styles/base.css`, `primitives.css` (the shared looks: `.label`, `.head`, `.outlined`, buttons, fields, notices, the busy, empty and failed states, a fingertip's tap area), then one part per area (`frame`, `chat`, `request`, `settings`, `signin`, `player`, `phone`, `pages`, `logs`, `coaches`). `theme.test.ts` holds every part to the tokens: no colour, tint, type size, spacing or control size typed by hand, colours only by their role, lines and lifts, weights, layers, line heights, opacities, durations and focus rings only from their tokens, corners only from the corner tokens, the four breakpoints (and `lib/breakpoints.ts`, the script's copy, at one of them), every control smaller than `--hit` given a full tap area on a touch screen, and no hover look on a disabled control.
- **`lib/`**: logic, with no markup: the server's API (`api.ts`, with `waitForJob`, the one loop that waits on a background job), the conversation (`conversation.ts`) and a turn's steps (`steps.ts`), the line breaks a message keeps (`lines.ts`), the browser's date and time (`when.ts`), how numbers, prices, dates and times are written (`format.ts`, the only file that calls `toLocale…`), the request's words (`request.ts`: `requestParts`, the one source of the first screen's sentence, the demos' and what's sent) and the body chart's marks (`bodyMarks.ts`), the backgrounds' shapes and painters (`skyPaint.ts`), the chat box's unsent text (`draft.ts`), asking Settings to open a key's row (`keyAsk.ts`), a form's rules checked once tried (`useChecked`), the keys (`keys.ts`, `useBalances`), reduced motion (`motion.ts`), the script's breakpoint (`breakpoints.ts`), the words for a failure the server didn't explain (`messages.ts`, the only file that says "Couldn't …"), what kind of site this is (`site.ts`: whether sign-in goes through Clerk and whether it runs on minutes, read from a context, and how a count of minutes is said), the listener's minutes (`useMinutes`, read again as a turn starts and ends and after the checkout page), trading a Clerk session for the site's own (`useClerkSession`), whether this browser has signed in before and is leaving (`visits.ts`), the Logs page's order and filters (`arrange.ts`), what the coach took from a workout's feedback (`useFeedbackNote`), loading a screen's data (`useResource`: the answer, the reason it failed, `reload`, and `refresh`, which keeps the answer shown while it asks again), a button's call to the server (`useAction`: busy, the error and the field it's about; `optimistic` and `useSaved`: change at once, put back with the reason), the first screen's request (`useStartInfo`, with the reason it failed and `reload`), Logs' and Coaches' addresses (`usePage`: `#logs`, `#coaches`) and a panel that holds the keyboard (`useFocusTrap`).
- **`ui/`**: the shared pieces: `Button` (every button outside `ui/`: busy, pressed and disabled in one place), `Field` (a label, hint and error tied to the input), `Notice`, `Loadable`, `Failed` and `Empty` (errors, notes, loading with Try again, a later failure said above what's kept, an empty list with the one thing to do next), `Boundary` (what shows if a page breaks while drawing: around the app and each signed-in page), `Section` (a Settings section and its heading), `PageHeader` (a page's title, which takes focus as it opens, and Close), `LevelCards`, `LinkButton` and `FileButton` (`ActionLink.tsx`: a link and a file picker drawn as buttons), `Popover` (a list under its control, or a modal dialog drawn on the body that puts the page to sleep), `ConfirmInline` (asking before a delete, with a field when something must be typed first), `Player` (`AudioPlayer`, the one player for workouts, samples and demos, one clip at a time), `AudioFile`, `RequestLine` (the request's two lines), `Flap` (letters that roll in, and `FlipWords`, words that flip in), `Mark` and `brand.ts` (the logo; `assets/brand/make.py` writes `brand.ts`), `Sky` (the background), `icons`, `Solo`, `PasswordForm` and `ClerkGate` (Clerk's provider and sign-in form in the site's look, the only file that imports Clerk's package).
- **`zones/`**: the pages and their parts (`SignIn`, `Demos`, `chat/` with `Chat`, its offer cards `Offers` and `Working`, `Starter`, `BodyChart`, `Ready` (the ready-made workouts), `logs/` with `Logs`, `WorkoutRow` and `FeedbackForm`, `Coaches`, `settings/` with the drawer `Settings` and a file per section: `KeysBox`, `MinutesBox` (in its place on a site that runs on minutes), `LevelBox`, `RecordBox`, `FeedBox`, `SkyBox`, `FilesBox` and the foot's `Account`). A page may show another page's component, but takes no helper from it, and `lib/` and `ui/` never reach into a page. Every `.tsx` but `App.tsx` and `main.tsx` is in `zones/` or `ui/`, and every `.ts` in `lib/` (but `ui/brand.ts`); no page keeps its own still-mounted flag or asks the server in a bare effect, no raw button outside `ui/` but three named custom widgets, no element outside it takes a button's look or a shared piece's, a submit button that waits names what it's doing (`busyLabel`), and a page marks no busy line of its own (`layers.test.ts`). Stop and cancelling a scheduled workout ask first (`ConfirmInline`), as every delete does.
- **A lost session** is handled once: `api.ts` tells the app (`setAuthLost`) on any 401, and the pages just let `NotSignedIn` go.
- **What the page offers for an error** comes from the server's `code` beside its words (`webapp/codes.py`: a step's `kind`, and a 402's `no_minutes` on a refusal or a failed job, `routes/billing.py`), never from the wording.

## Deploy

The web client runs on Fly.io (`fly.toml`, app `harmonicfitness`, region `iad`). The root `Dockerfile` builds one image (the client built in a Node stage, then the engine and `web/` on `python:3.11-slim` with ffmpeg and the `web` extra only: no local voices), which Fly runs as two process groups, told apart by `HARMONICFITNESS_ROLE`; `web/entrypoint.sh` starts the right one:

| Process | `HARMONICFITNESS_ROLE` | Runs |
|---|---|---|
| web | `web` | uvicorn on `$PORT` (8000, set in `fly.toml`): applies the migrations, then serves the API and client, behind Fly's proxy. Its health check is `/healthz`. |
| worker | `worker` | `python -m webapp.worker`: waits until the migrations are applied (up to two minutes, then exits 3), then runs jobs (`HARMONICFITNESS_WORKER_SLOTS` turns at once, default 2), reconnecting when the database drops it. |

Secrets (`fly secrets set`, shared by both groups): `DATABASE_URL` (the managed Postgres cluster's direct address, not PgBouncer: the worker LISTENs), `HARMONICFITNESS_BASE_URL` (the public address, `https://harmonicfitness.fly.dev`), `HARMONICFITNESS_MASTER_KEY` (32 random bytes, base64; keep a copy: files stored under another key can't be read) and `OPENROUTER_API_KEY` (the site's own key: it writes and speaks every workout). Optionally `HARMONICFITNESS_REGISTRATION` (`open`, the default, or `closed`) and `HARMONICFITNESS_WORKER_SLOTS` (turns a worker runs at once, 1 to 4, default 2; 1 if its memory runs short). For sign-in through Clerk, `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY`; for minute packs, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (the endpoint's, from `stripe_setup`) (the web service refuses to start on half of a pair). `HARMONICFITNESS_HOSTED` and `HARMONICFITNESS_PROVIDERS`, from before 0.88.0, are ignored and can be unset. Values never go in `fly.toml`, since the repo is public.

**Deploys come from CI:** every push to `main` that passes the privacy job, the web tests and the engine tests (or skips the engine tests, for a push that changes only `web/`, the changelog or the version) runs `flyctl deploy --remote-only --build-arg GIT_COMMIT_SHA=<commit>` (`.github/workflows/test.yml`, with the `FLY_API_TOKEN` secret), so only committed files reach the server, and `me/` is never one of them (`.dockerignore` leaves it out too). By hand, from the repo root: `fly deploy --build-arg GIT_COMMIT_SHA=$(git rev-parse --short HEAD)`. The commit shows beside the version at the foot of Settings ("Version 0.78.0 (abc1234)"), so a deploy can be checked; the header shows the release alone.

The repo is `/app` and its environment `/app/.venv`, which `./harmonicfitness` finds on its own; `HARMONICFITNESS_PYTHON` names it, so a job never runs uv or reaches the network. The container runs as a non-root user.

**Admin on Fly:** open a shell in a running web machine with `fly ssh console --process-group web`, then

    cd /app/web && python -m webapp.admin reset-password <username>
    cd /app/web && python -m webapp.admin grant <username> <minutes>

(`python` is the image's environment, and the secrets are in the shell's environment.)
