# web/

The web client for HarmonicFitness, called "HarmonicFitness" in the app itself: a FastAPI server (`webapp/`) that runs the engine for a listener from a browser. It is an optional extra; a command-line install doesn't grow.

Install its dependencies:

    uv sync --extra web

On a computer that also has local voices, keep the voice engine's extra too (a sync without it uninstalls PyTorch):

    uv sync --extra cpu --extra web

Run its tests (`./harmonicfitness test` runs them after the engine's, or prints a skip line when the extra isn't installed):

    .venv/bin/python -m unittest discover -s web/webtests -t web -v

Set `HARMONICFITNESS_TEST_DATABASE_URL` (for example `postgresql://postgres@localhost:5432/postgres`) to a Postgres database to enable the database tests; without it they are skipped.

## Admin

People make their own accounts (username and password) while registration is open. Set `HARMONICFITNESS_REGISTRATION=closed` on the web service to stop new accounts; sign-in keeps working. A refused username or password (`POST /api/register`, `POST /api/password`) answers `{"detail": "<why>", "field": "<the box>"}`, the field being `username`, `password`, `current` or `new`, so the page says it under that box.

For someone who forgot their password, run from `web/` (or with `web/` on `PYTHONPATH`), with `DATABASE_URL`, `HARMONICFITNESS_BASE_URL` and `HARMONICFITNESS_MASTER_KEY` set:

    python -m webapp.admin reset-password <username>

It clears their password, signs out their devices and prints a one-time sign-in link (24 hours) and nothing else; send it to them yourself. Opening it signs them in, and the app asks for a new password. It never migrates: against a database still missing a migration (one the web service hasn't applied yet) it refuses, exits 1, and says to deploy first.

## Keys

Each listener's voice service keys (one per web voice service in the engine's `knowledge/services.toml`) are entered in the app's Settings panel (the gear, top right) and stored in the `user_keys` table (migration 005), one row per user and service, sealed with that user's data key; only the service name and a timestamp are plain. A key is trimmed, must be printable ASCII with no spaces (the engine's `keys.clean_value`) and 16 to 1024 characters.

The web process seals a key on entry and never opens one: `GET /api/keys` says only which services have a key, `PUT /api/keys/<service>` sets or replaces one and `DELETE` removes it. `POST /api/balances` queues a `balances` job (one waiting or running is returned instead of another), which runs `./harmonicfitness balances --json` with the listener's keys and keeps only the numbers Settings shows (never the service's own words); Settings shows what's left where Fish Audio and ElevenLabs say, and a link to each other service's billing page. Only the worker opens a listener's keys, for a job, and passes them to the engine under the variable names in `services.toml` (such as `FISH_AUDIO_API_KEY`); the engine's output is scrubbed of them.

Every job runs the engine with `HARMONICFITNESS_WEB=1`: no local voices, "add a key" messages point at the app, a stock web coach by default, and the finished MP3 is kept for the app to upload.

## Agent

The app is a chat, a Settings drawer (tabs for the listener's keys, their level, Record without asking, the background and their files, one shown at a time, with their account always at its foot) and the Coaches and Logs pages. The level is picked from three cards, each a short name over the sentence that fits them (`GET` and `PUT /api/level`, `webapp/level.py`; `GET` reads only the profile's four files): novice until one is chosen, as the engine plans, and saved with the engine's `set experience`, every other line of the profile kept. The coach works as Claude Code does on a listener's computer: one agent (Pydantic AI) follows the workout skill itself (`.claude/skills/workout/SKILL.md`, read from the engine at run time; `research.md` is for a computer's research agents, so it isn't given) under a short preamble (`webapp/agent/instructions.md`) that says what the web client offers in place of each Claude Code tool, as `AGENTS.md` does for Codex. Questions are asked in the chat and research is done in turn. A new listener (no experience level in their profile yet), or one who asks to be set up, also gets the setup skill: its quick start in the chat, keys added in Settings, the stock web coach for a keyed service made with `coaches make` (its sample plays in the chat), then a ten-minute first workout. The check-in may change `health.md`, with the listener's permission, as the skill says.

**Recording costs money, so it waits for the listener.** A full build is first only priced: the `run` tool lints the draft (skipped when the same text just linted clean with the same coach), takes the character count the lint prints for a web voice and prices it (`get cost`), and keeps the offer in the conversation; the chat shows a Record button with the price, on a card that also shows the plan, worked out by the engine from the draft's own segments (`get plan --draft`, read beside the price, so its times always add up) and, before the first build that sends a script to a voice service (`get web-builds` is 0), where the script goes and what that means (the privacy line), so the model writes neither. With **Record without asking** on in Settings (`users.auto_record`, migration 014, off by default; `PUT /api/auto-record` with `{"on": true | false}`, returned by `GET /api/me`), a clean price records at once in the same turn: the worker reserves the characters from today's allowance as the Record endpoint does, and past the allowance the offer stays and the Record button says why. `POST /api/conversations/{id}/record` reserves those characters from today's allowance (`spend`, `HARMONICFITNESS_DAILY_CHARS`, default 180,000 a day) and queues a turn in which the same build runs, with `--max-chars` set to the approved count. That turn loads the listener's kept clips (`clip_cache`, sealed, a week), so a re-record sends only lines that changed, and keeps the new ones. The worker keeps each MP3 the turn made (`media`, sealed with the user's data key) and adds it to the chat as a player with a download: a workout's until the listener has three newer ones (making a fourth deletes the oldest, migration 017), any other for 24 hours. `GET /api/media/{id}` serves it to its owner only (byte ranges for Safari; `?download=1` for a download; `Cache-Control: private`), a conversation marks a recording no longer kept `gone` so the page says so, and the worker deletes MP3s past their time and week-old clips. MP3s never go into the store, except a coach's sample (`coaches/<slug>/sample.mp3`, `folder.COACH_SAMPLE`), which the Coaches page plays through `GET /api/coaches/{slug}/sample.mp3`: the listener's own copy first, else the one the engine ships. One approval records once: the approved build spends it, and once it has made an MP3 (exit 0, or 2 when the total ran a little off plan) the workout is final for the turn (another build or a rewrite of its draft is refused). As soon as it has, the worker keeps what it made (the files written back, a coach designed for it among them, the clips and the MP3), so a turn that then stops or fails loses none of it, and the failed conversation still shows the audio. Each kept MP3 names the build that made it (`media.build_id`, from the build record beside it), and `GET /api/workouts` adds a logged workout's MP3 while it's kept (the three newest), which the Logs page plays.

**A workout for later** (0.60.0). The page's sentence ends ", right now" or a time the listener picks, every half hour for the next day ("at 7:00 PM", "tomorrow at 6:30 AM"); with a time, `POST /api/conversations` carries `start_at` (ISO with the browser's offset), and the conversation keeps it as `later` (a time inside fifteen minutes runs at once; one past a day is refused). The first turn is the check-in only: the worker tells the agent the time, `brief` is refused until the later turn, and once nothing's left to ask the agent calls `schedule_workout` (offered only then), which prices the session's minutes with the coach (`get cost` at 650 characters a minute for the estimate and 800 for the ceiling, as priced scripts run) and ends the turn. The chat shows the estimate, the ceiling and **Schedule it**: that press is the one approval. `POST /api/conversations/{id}/schedule` queues a `turn` job with `jobs.not_before` fifteen minutes before the time (migration 016; `jobs.claim` skips a job until it's due, and a job not yet due doesn't count toward the queued cap) and moves the conversation to `scheduled`, where it takes no messages. When the job is claimed the worker wakes the conversation (`conversations.wake`: only for that job, so a cancel that raced the claim leaves it alone), sets the listener's date and time from their offset as it is then, and runs the turn with Record without asking on and the ceiling as its limit: a clean price under the ceiling records at once, within today's allowance; one over it waits with the Record button and its real price. `POST /api/conversations/{id}/cancel` fails the queued job ("cancelled") and puts the conversation back to idle with its plan kept; once the turn has begun, Stop ends it. The page reads a scheduled conversation every 30 seconds to see its writing begin, and the worker logs how long after its due time each scheduled turn began.

**Stop.** `POST /api/conversations/{id}/stop` flags the running job; the heartbeat looks every two seconds and sets the job's cancel event, which cancels the model run and kills the engine's process group (`engine.run(cancel=)`), so nothing keeps billing. The conversation says "Stopped."

**Logs.** The Logs button beside the gear opens a page of the listener's logged workouts (the chat stays as it was, behind it): each one's date, length, format, kit, coach, movements, topics and feedback, its script on request, a rating (positive, neutral or negative; pressing it again clears it), a line of feedback, and delete (after a confirm), with search, filters (rating, format, kit) and sorting in the page. `webapp/workouts.py` runs the engine's `workouts` command on the listener's files in a temporary folder, as `/api/start` does: `GET /api/workouts`, `GET /api/workouts/{ref}/script`, `POST /api/workouts/{ref}/feedback`, `PUT /api/workouts/{ref}/rating` and `DELETE /api/workouts/{ref}` (its folder and files too), where `ref` is the build id, or the workout's number when it has none. A change is written back against the versions read; a turn saving at the same moment makes it a 409, to try again.

**Learning from feedback.** A feedback line saved on the Logs page (`POST /api/workouts/{ref}/feedback`, now 202 with `{"job_id"}`) queues an `enrich` job, which runs in a lane of its own (migration 015: `one_running_job_per_user` now leaves enrich jobs out, and `one_running_enrich_per_user` keeps those to one a user; the worker runs a second loop, `serve(lane="enrich")`, beside the main one), so it never waits behind or blocks a workout. It runs `./harmonicfitness workouts context <ref>`, makes one structured request on the listener's writer key (`webapp/agent/enrich.py`: up to twelve signals and a summary, with the writer's web search to pin down a name; the shape has no field for health), applies the signals with `interests add --source feedback`, and saves the files at once; when a turn saved the evidence file at the same moment, it applies them again on the files as they stand, without a second model call. The Logs page follows the job (`GET /api/jobs/{id}`) and shows its summary under the workout. A rating needs no model: the engine's `workouts rate` writes its signals itself. "Tell me what you enjoyed" on the first screen fills in "Lately I enjoyed " for the listener to finish; the turn treats it as one job (`agent.ENJOYED` keeps "I enjoyed a 5k run" from reading as a workout request), records it with `interests add --source mention`, and says what it picked up.

**Syncing with a computer.** `./harmonicfitness sync` signs in as the listener and keeps their computer's `me/` in step: `GET /api/sync` lists each file the site keeps (path, version, sha256), `POST /api/sync/read` returns bodies (base64), and `POST /api/sync/write` applies each change through `store.write_back` over the version the computer last saw, so a file a turn saved since is a conflict, left as it is. Paths the site never keeps (`folder.SKIP`, but each coach's `sample.mp3`) and auditions are refused.

**Leaving.** `GET /api/export` is every file as a ZIP laid out as `me/` (keys are never files here). `POST /api/account/delete`, with the password, deletes the user row and everything that hangs from it.

Its seven tools (`webapp/agent/tools.py`, and `write_script` and `schedule_workout` in `webapp/agent/__init__.py`):
- `run`: one `./harmonicfitness` command in the listener's folder (five minutes; a full build gets the workout's own length, at least ten, and the turn's clock waits for it). Allowed: brief, build (not `--follow` or `--clips-only`), check, content, coaches (list, last, measured, make, forget-audition, archive; never `audition` or `keep`), coverage, feeds, get, help, interests, keys, log-session, movements, topics, workouts, youtube. A voice design (`coaches make`) gets 10 minutes. `me/...` paths in arguments become the folder's own; any other path is refused.
- `read_file`: `me/...` (never `me/.env`) and the engine's `knowledge/`, `.claude/skills/` and `coaches/`.
- `write_file`: `me/...` only; never `me/.env`, the kinds of file the store doesn't keep, or an audition's own files (only its narrative, `me/coaches/.auditions/<slug>.md`).
- `edit_segments`: segments of a draft by their places (the lint's # column), each the whole new segment with its `@@` line first, all in one call and all or nothing: a lint's fixes go in one request, not the whole script again and not one segment a request. Refused once the draft is recorded. It and `write_file` say what a draft's segments add up to, so a length that misses the request is caught before the lint.
- `list_files`: under `me/`.
- `schedule_workout`: prices a workout for later and ends the turn (A workout for later, above); offered only then.
- `write_script`: fills a skeleton with the script's words (the draft's path, `build_name` and `coach`), then builds it, as `write_file` does. A clean skeleton no longer needs it (it goes straight to the writers' room, below); it stays for a skeleton written before. It runs the writers' room (`webapp/agent/writers.py`), the site's default; `HARMONICFITNESS_WRITERS=one` takes the tool away, and the agent writes the words itself in passes with `edit_segments`.

**The writers' room.** The agent plans the session and writes the skeleton with `write_file`: every segment's seconds, counts, holds and `[reps N]`, each set's dose and weight in its label, each rest a segment of its own labelled just `Rest` (or `Transition`: never a topic or a movement's name), and an empty `[story] [/story]` after the go of each steady timed set that will carry a story. A skeleton within ten percent of the request is settled by the site, the difference spread over its rests (`tools.settle_clock`). Its lint gives each segment's word budget, and once that lint is clean the same `write_file` (or the `edit_segments` that fixed it) hands the words to the room at once, with no model request between (`agent._chain`). Four writers, each a model call on the listener's writer key, each given only its own task (`researcher.md`, `trainer.md`, `host.md`, `review.md` beside it) and its own parts of `knowledge/script.md` and `knowledge/tts-rules.md`:
- **The researcher** starts as soon as the brief is saved (`brief --save`), while the agent plans the skeleton. From the listener's topics, the content plan, the stock, today's sheets and its own web searches, it returns each story as notes (why it's theirs, the facts, the point), marked for steady work or a rest. A story the plan lists as told before is dropped for a spare, and asked for again only when too few would be left. It writes before the skeleton exists, so when the skeleton has more places than it wrote for, it's asked for the rest while the trainer works (`writers.top_up`), going on from its own run.
- **The trainer**, at the same time, turns the brief and the movements' coaching notes into notes for each segment, sized to the words the plan gives it (and, where a story goes, the words left for the coaching around it), with the safety points as plain notes: no label in front of one, so nothing meant for the host can be read aloud.
- **The host**, the coach's voice, writes every segment from both, to about its budget, as one person talking. Code places the stories: each rest, and each marked steady set, takes the next story that suits it, and the spares go when there are fewer places. A story gets about 70 percent of a rest's words and 55 percent of a steady set's, but always leaves the coaching at least 60 (`writers.COACHING_FLOOR`), what a breath, a self-check and what's next take; the host is told both shares. A rest left without a story is told so, and that its label is no story to tell; a story the host tells there anyway is taken out before the review, which fills its time with coaching (`writers.without_unasked`). A fixed hold or pause over eight seconds is taken out, and the coach talks through those seconds instead.
- **The trainer's review** checks what matters to the body (the opening's rules and that an AI wrote it, each limit's side, its one reminder) and the build's check (`--lint-only`), fixing only what fails and leaving the host's voice alone. Each of its edits is checked again, and it goes round again while the check still finds something, up to three rounds (`writers.REVIEWS`): the room never hands back an edit nobody checked. A clean lint here is remembered, so the build after the room prices the same text without linting it again.

The researcher and the review think at LOW, the trainer and the host at MEDIUM (`writers.LEVEL`): at MEDIUM the researcher took 78 to 160 s and held the room up for most of that, at LOW 17 to 27 s. A writer that runs past its patience (`writers.PATIENCE`), or is cut off by Gemini's own deadline, is asked again thinking less. When the room is done, the draft builds and prices as any other, and the agent fixes what's left with one `edit_segments`. The worker's log has a `room` line for each writer (its level, seconds, tokens and searches, and whether it was asked again), each lint, how long the room waited for the researcher, and the room's whole time: never what any of them read or wrote.

**The bench.** `web/bench/` times the room from the brief to the price on the maintainer's own key and reads the scripts for what matters to the listener; its README has the method, the rule for keeping a change, and every result so far.

**Web search.** The writer has its own provider's web search (Gemini's Google Search, Claude's, ChatGPT's, OpenRouter's; `agent.SEARCH`, pydantic-ai's `WebSearchTool` as a run capability, low context, at most eight a turn where the provider takes a cap), billed by that provider on the listener's key. In the writers' room only the researcher searches (the agent is told not to): about six a workout, for the topics due the feeds don't cover, what's on at their venues and near them, and quick hits for the work, and only a source from the past two weeks makes something news. With `HARMONICFITNESS_WRITERS=one` the agent runs the same six itself, after the check-in. The turn's log line counts them, the room's included.

**Logging, after the recording.** Once a recording is made, the site logs it itself, so the model spends no request on each: the stories the writers' room told (`content log`, from the room's own list), and the `log-session` the agent sent ahead of the recording (in the same reply as the skeleton). A `log-session` for a draft not recorded yet is kept ("Kept", a success on the listener's steps as "Noting the session for your log") and run the moment the recording is made; both ride on the offer, so a Record button's turn has them. Either one refused goes back to the model in the recording's result, to fix and run itself.

**Topics, quickly** (0.63.0). The page's "I'd like to update my interests." (or "add a topic", with nothing named) is answered at once by the worker, with no model request: "What's on your mind? ... Or do you want me to offer some trending topics?" (`agent.TOPICS_OPENER`), kept in the history as the model's reply. A topics job (`agent.topics_job`: asked for now, or the conversation began with it, and the line asks for no workout) is a light turn: no workout skill or writing guides, no web search, no background `feeds`, and in place of step 1 only content.md's topics, venues and never-bring-up lines. The agent adds what they name with `topics add`, whose `--feed` finds a site's, newsletter's or podcast's feed itself; trending ideas come from `content trending`. A workout asked for after the opener reads step 1 as a first turn would.

To save round trips, the worker does three things itself. The instructions carry `knowledge/script.md` and `knowledge/tts-rules.md` after the skill, so the model never reads them. With the writers' room, `script.md` stops before its craft ("Getting the workout done" on), which the writers read instead. On a conversation's first turn it runs step 1 of the skill before the first model request, all at once (`check`, `content plan` for the length the request names (else 25), `get coach`, the coach's `get route`, `coaches list`, `get web-builds`, today's workout folders, and reads of `profile.md`, `training.md`, `health.md` and `log.md`), and hands the results to the model with the listener's first message. It starts `feeds` in the background as a turn begins, once the check-in is answered (each later turn, or a set-up listener's first turn when it asks for a workout, which the page's sentence answers), unless today's sheet is already there; a `feeds` run in the turn (the writers' room's, or with `HARMONICFITNESS_WRITERS=one` the model's) waits for that run instead of starting another, and the turn ends only once it has finished. In the writers' room the agent itself doesn't run `feeds`: the researcher reads the sheet and the host gets the weather.

**The worker's log** has a line for each step of a turn with how long it took (`run build --lint-only exit 1 4.8s`, `think 76.1s` for a model request, `edit_segments exit 0 0.0s`) and one for the whole turn (its seconds, model requests and tokens in and out): never what was read, written or said. `./harmonicfitness pull` saves the model's side of the latest conversation as `history.json`, for the listener's own look at what each step did.

**A coach of their own** is made on a computer, not here. On the site a listener picks from the stock web coaches on the **Coaches** page, and the agent points them there when they ask for a new coach or a different voice. `coaches audition` and `coaches keep` are refused. A coach they made before stays theirs, and an audition left open from before is closed with `coaches forget-audition`, which deletes Gemini's unkept voices.

Safety is the engine's: the brief's safe menu and the build's menu gate (movements off the menu, one side only, names the catalog doesn't hold) refuse what the writer gets wrong, as does its check that a one-sided limit's side is named in the opening.

A conversation is a series of short `turn` jobs. Each runs one turn in the listener's temporary folder with their own language-model key, then saves the conversation (its history and chat lines) sealed with their data key, and writes back the files its folder changed, never `health.md`. A turn stops at 60 model requests, 120 tool calls, 3,000,000 tokens or fifteen minutes (longer while a recording runs); nothing is retried (`max_retries=0`, 180 seconds per request).

The providers are Claude (`claude-sonnet-5-5`), ChatGPT (`gpt-6.1-sol`), Gemini (`gemini-3.8-flash`) and OpenRouter (`anthropic/claude-sonnet-5.5`, on the same key as its voices; `webapp/providers.py`); `HARMONICFITNESS_PROVIDERS` names the ones offered, on both services (default all of them). `PUT /api/writer` picks which offered one writes the listener's workouts. A model key is stored like a voice key, and only that job's model client holds it: the engine's environment never gets it.

While a turn runs, the chat shows each step in plain words ("Checking today's safety limits", "Recording your workout"), never a command or a file's name, and, while the model itself works between steps, a live line saying what it's thinking about ("Reading your message", "Writing your script"), which goes once it's done. A step running longer than eight seconds shows its own clock, and past 25 seconds a line says why it's a long one. A listener not set up yet who asks for a new coach gets the coach first; setup waits until it's made.

The model provider sees the files the agent reads (the profile, health and log among them), the engine's output, the skill, the chat, and the local date and time.

The page opens fresh: a finished conversation isn't shown again. It opens on one that isn't done: one still working, which it follows (a reload in the middle of a turn keeps its steps and Stop), or one from today waiting on the listener (the coach spoke last, or a Record offer is open), as long as it hasn't failed or recorded a workout yet. "New workout" clears the page; the next message starts a new conversation, as does a message after a conversation from an earlier day.

**Before signing in.** The sign-in page shows what seven invented listeners asked for (`client/src/zones/Demos.tsx`), one at a time, each as the request the app would send for them ("Hey, coach Priya, I'd like a 30-minute full-body workout in a hotel room, right now. Go easy on my left knee today."), with two minutes of the workout it made to play from the media bucket, and who asked, their kit, what changed for them and the moments behind one tap. It turns every ten seconds until someone plays, taps or tabs in. `client/src/demos.json` is written by `./harmonicfitness demos web` from `docs/demos/demos.toml`; nothing is asked of the server.

**The first screen.** `GET /api/start` gives what the page's opening sentence is filled in with ("Hey, coach Reed, I'd like a 25-minute strength workout at home. Go easy on my left knee today."; each blank opens its choices, and the second line opens a body chart: areas head to feet, each side a three-way toggle tapped from OK to "go easy" to "keep off"): the web coaches, stock and the listener's own, each with whether its service has a key here, the one used last (else the first with a key) first and marked current; the profile's kits, then the engine's presets, each with words for "at ..." ("a hotel room"); the usual length from the profile's Default session (10 to 60, else 25; ten for a new listener with no level yet, the quick start's first workout); `health.md`'s limits; a suggestion from `coverage` (a body part not trained this week, or the days since the last session; null with nothing to say); and whether setup is still quick. It writes the listener's files to a temporary folder and runs `coaches list --json` and `coverage --json` there, side by side; it changes nothing. The answer is kept in the web process per listener (`start.cached`, an hour at most) under what it was made from: the files' versions (`store.fingerprint`, read from the rows without opening a path or body), the keyed services, the chosen coach and the day; any change to one makes a fresh answer, and signing out or deleting the account drops it. The page shows the sentence as soon as it knows the keys, its blanks rolling in when the answer comes, and asks again only when a key changes. The sentence goes as the first message, and the agent takes its answers as the check-in's (`agent/instructions.md`); a limit from `health.md` can be tightened there for the day, never loosened. Below it, "Or ask for something else" lists the other common asks, each with a line saying what it does (an injury, equipment, what fills the rests, a coach, feedback).

**The look.** Moonrise, after Ansel Adams' "Moonrise, Hernandez": dark only, with a faint moving pattern behind every page (`client/src/ui/Sky.tsx`), the listener's choice in Settings (`ui/Sky.tsx`'s `SKIES`, painted by `lib/skyPaint.ts`): Flow (fine lines drifting sideways, an SVG translated in a loop), Field (a grid of dots on a canvas, crossed by a ripple from the top right every seven seconds), Waves, Bloom, Woven Grid or Node Garden. All hold still under the system's reduced-motion setting and brighten a little while the coach works. The choice is saved per account (`users.sky`, migration 011, null meaning Flow): `GET /api/me` returns it as `sky`, and `PUT /api/sky` with `{"sky": "flow" | "field" | "waves" | "bloom" | "woven" | "garden"}` sets it (anything else is 422; `keystore.SKIES`). Big Shoulders Display for headings, the request and buttons; IBM Plex Sans Condensed for the rest; the logo's coral for the request's fixed words and, in Settings, a small mark on what's chosen (the `--accent` role), cream for everything you act on.

Routes: `GET /api/me`, `PUT /api/sky`, `PUT /api/auto-record`, `PUT /api/coach` (`{"slug", "day"}`: the coach chosen in Settings or the sentence, kept in `users.coach` and `coach_day`, migration 012, as the first screen's coach and the chat's until a workout logged on a later day used another), `GET /api/start`, `POST /api/conversations`, `GET /api/conversations/latest`, `GET /api/conversations/{id}`, `GET /api/conversations/{id}/history` (the model's side, its owner only, for `./harmonicfitness pull`; the page never shows it), `POST /api/conversations/{id}/messages`, `.../record`, `.../schedule`, `.../cancel` and `.../stop`; `GET /api/media/{id}`; `PUT /api/writer`; the level, keys, balances, jobs (`GET /api/jobs/{id}` and its `/events`), workouts and coach sample routes above; `POST /api/import`, `GET /api/export`, `GET /api/sync`, `POST /api/sync/read` and `/write`, `POST /api/account/delete`.

## Run it locally

With Postgres running and the web extra installed (`uv sync --extra web`), one command runs the server and the worker together in one terminal, each line labeled `[web]` or `[worker]`; Ctrl-C stops both:

    web/dev.sh          # builds the client, then serves it at http://localhost:8000
    web/dev.sh hot      # adds Vite at http://localhost:5173, which reloads as you edit the client
    web/dev.sh reset    # deletes the local database and key, for a fresh start

It makes the database `harmonicfitness_dev` (`HARMONICFITNESS_DEV_DB` changes it) and a master key in `.cache/webdev/` (git-ignored) the first time, and keeps both between runs. `HARMONICFITNESS_PROVIDERS`, if set in your shell, passes through.

## Serve

Run from `web/`, with `DATABASE_URL`, `HARMONICFITNESS_BASE_URL` and `HARMONICFITNESS_MASTER_KEY` set (the same as the admin commands). It applies any database migrations once at startup, then serves the API and, when `web/client/dist` has been built, the client:

    uvicorn webapp.api:create_app_from_env --factory --no-access-log --host 0.0.0.0 --port 8000

`--no-access-log` matters: a one-time sign-in link's page is `GET /link/<token>`, so an access log would write those tokens to the logs. The server itself logs no token, job argument, event or result.

The session cookie is `Secure` unless `HARMONICFITNESS_BASE_URL` starts with `http://localhost` or `http://127.0.0.1`, so local development works over plain http. Every POST must carry an `Origin` (or `Referer`) of `HARMONICFITNESS_BASE_URL`'s origin, so set it to the address the browser uses.

## Client

The browser client is in `client/` (Vite, React and TypeScript; Node 20 or later). From `web/client`:

    npm ci
    npm test          # the client's own tests
    npm run build     # writes dist/, which the server above serves
    npm run dev       # a dev server on :5173 that sends /api and /link to the server on :8000

How `client/src/` is laid out:

- **`tokens.css`**: every colour, tint, size, space, corner, line height, opacity, focus ring, layer and duration, the one list, with the four breakpoints in its header. Its palette (`--ink`, `--sheet`, `--stop`…) is what the roles are made of; the stylesheets use only the roles (`--text`, `--text-muted`, `--surface`, `--border`, `--action`, `--danger`, `--sample`…), so a second theme would redefine the roles alone. `docs/tokens.css` is an exact copy and the web player page (`tools/webcopy.py`) inlines it (`tests/test_tokens.py`).
- **`theme.css`** is only the list of the stylesheet's parts, in cascade order: `styles/base.css`, `primitives.css` (the shared looks: `.label`, `.head`, `.outlined`, buttons, fields, notices, the busy, empty and failed states, a fingertip's tap area), then one part per area (`frame`, `chat`, `request`, `settings`, `signin`, `player`, `phone`, `pages`, `logs`, `coaches`). `theme.test.ts` holds every part to the tokens: no colour, tint, type size, spacing or control size typed by hand, colours only by their role, line heights, opacities, durations and focus rings only from their tokens, corners only from the corner tokens, the four breakpoints, and no hover look on a disabled control.
- **`lib/`**: logic, with no markup: the server's API (`api.ts`, with `waitForJob`, the one loop that waits on a background job), the conversation (`conversation.ts`) and a turn's steps (`steps.ts`), the line breaks a message keeps (`lines.ts`), the browser's date and time (`when.ts`), how numbers, prices, dates and times are written (`format.ts`, the only file that calls `toLocale…`), the request's words (`request.ts`: `requestParts`, the one source of the first screen's sentence, the demos' and what's sent) and the body chart's marks (`bodyMarks.ts`), the backgrounds' shapes and painters (`skyPaint.ts`), the chat box's unsent text (`draft.ts`), asking Settings to open a key's row (`keyAsk.ts`), a form's rules checked once tried (`useChecked`), the keys (`keys.ts`, `useBalances`), reduced motion (`motion.ts`), loading a screen's data (`useResource`: the answer, the reason it failed, `reload`), a button's call to the server (`useAction`: busy, the error and the field it's about; `optimistic` and `useSaved`: change at once, put back with the reason), the first screen's request (`useStartInfo`, with the reason it failed and `reload`), Logs' and Coaches' addresses (`usePage`: `#logs`, `#coaches`) and a panel that holds the keyboard (`useFocusTrap`).
- **`ui/`**: the shared pieces: `Button` (every button outside `ui/`: busy, pressed and disabled in one place), `Field` (a label, hint and error tied to the input), `Notice`, `Loadable` and `Empty` (errors, notes, loading with Try again, an empty list with the one thing to do next), `Popover` (a list under its control, or a modal dialog drawn on the body that puts the page to sleep), `ConfirmInline` (asking before a delete, with a field when something must be typed first), `Player` (`AudioPlayer`, the one player for workouts, samples and demos, one clip at a time), `AudioFile`, `RequestLine` (the request's two lines), `Flap` (words that roll in), `Mark` and `brand.ts` (the logo; `assets/brand/make.py` writes `brand.ts`), `Sky` (the background), `icons`, `Solo` and `PasswordForm`.
- **`zones/`**: the pages and their parts (`SignIn`, `Demos`, `chat/` with `Chat`, its offer cards `Offers` and `Working`, `Starter`, `BodyChart`, `Logs`, `Coaches`, `Settings`, `KeysBox`). A page may show another page's component, but takes no helper from it, and `lib/` and `ui/` never reach into a page. Every `.tsx` but `App.tsx` and `main.tsx` is in `zones/` or `ui/`, and every `.ts` in `lib/` (but `ui/brand.ts`); no page keeps its own still-mounted flag, and no raw button outside `ui/` but five named custom widgets (`layers.test.ts`).
- **A lost session** is handled once: `api.ts` tells the app (`setAuthLost`) on any 401, and the pages just let `NotSignedIn` go.
- **What the page offers for an error** comes from the server's `code` beside its words (`webapp/codes.py`: `no_model_key`, `key_refused` on a refusal or a failed job; a step's `kind`), never from the wording.

## Deploy

The web client runs on Fly.io (`fly.toml`, app `harmonicfitness`, region `iad`). The root `Dockerfile` builds one image (the client built in a Node stage, then the engine and `web/` on `python:3.11-slim` with ffmpeg and the `web` extra only: no local voices), which Fly runs as two process groups, told apart by `HARMONICFITNESS_ROLE`; `web/entrypoint.sh` starts the right one:

| Process | `HARMONICFITNESS_ROLE` | Runs |
|---|---|---|
| web | `web` | uvicorn on `$PORT` (8000, set in `fly.toml`): applies the migrations, then serves the API and client, behind Fly's proxy. Its health check is `/healthz`. |
| worker | `worker` | `python -m webapp.worker`: waits until the migrations are applied (up to two minutes, then exits 3), then runs jobs, reconnecting when the database drops it. |

Secrets (`fly secrets set`, shared by both groups): `DATABASE_URL` (the managed Postgres cluster's direct address, not PgBouncer: the worker LISTENs), `HARMONICFITNESS_BASE_URL` (the public address, `https://harmonicfitness.fly.dev`), `HARMONICFITNESS_MASTER_KEY` (32 random bytes, base64; keep a copy: files stored under another key can't be read) and `HARMONICFITNESS_PROVIDERS`. Optionally `HARMONICFITNESS_REGISTRATION` (`open`, the default, or `closed`). Values never go in `fly.toml`, since the repo is public.

**Deploys come from CI:** every push to `main` that passes the privacy job runs `flyctl deploy --remote-only --build-arg GIT_COMMIT_SHA=<commit>` (`.github/workflows/test.yml`, with the `FLY_API_TOKEN` secret), so only committed files reach the server, and `me/` is never one of them (`.dockerignore` leaves it out too). By hand, from the repo root: `fly deploy --build-arg GIT_COMMIT_SHA=$(git rev-parse --short HEAD)`.

The repo is `/app` and its environment `/app/.venv`, which `./harmonicfitness` finds on its own; `HARMONICFITNESS_PYTHON` names it, so a job never runs uv or reaches the network. The container runs as a non-root user.

**Admin on Fly:** open a shell in a running web machine with `fly ssh console --process-group web`, then

    cd /app/web && python -m webapp.admin reset-password <username>

(`python` is the image's environment, and the secrets are in the shell's environment.)
