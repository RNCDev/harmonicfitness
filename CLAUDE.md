# sweatcast: a workout podcast, made fresh each session

**Code introspection:** a codegraph index (`.codegraph/`, git-ignored) covers the engine; use the codegraph MCP tool (`codegraph_explore`) to find and read code, its callers and what a change touches, before grepping or reading files. After moving or renaming files, run `codegraph init` again to refresh it.

sweatcast turns a request for a workout into a narrated MP3 for earbuds, with no screen and no timer. The audio is the workout: it tells the listener what to do, keeps them company, and moves them along on time. The lint predicts each segment's spoken length for the chosen coach; the render lays segments on the plan's clock, and a segment with time to spare widens its paragraph breaks, then ends early rather than going quiet, unless a `[hold]` keeps it its full length for timed work. Only the total is held to plan, within three percent either way: a natural voice matters more than exact timing.

Priorities, in order: safe for the listener's body today, clean to the ear, worth listening to.

## What runs when

- **Any request for a workout, in any words,** runs the `workout` skill (`.claude/skills/workout/SKILL.md`): check-in (asked first, from the profile, health and log alone), research, the brief, design, script, build, log and backup. `./sweatcast brief` supplies the ingredients, the writer designs and writes the session, and the build refuses any movement the brief's menu doesn't hold.
- **Getting started** ("set up sweatcast", "set me up", "finish setting me up"), **or changing the profile, injuries, feeds, audio route or delivery,** runs the `setup` skill (`.claude/skills/setup/SKILL.md`), as does a workout request when `me/profile.md` doesn't exist yet. Its quick start asks one round of questions, adds one web key where local voices don't run (`keys init`, then `keys open`), gives the listener a stand-in coach and plays its test clip (Coach Andy locally; else the keyed service's default web coach, made then with `./sweatcast coaches make`), and ends with a ten-minute workout. The rest of the interview waits for "finish setting me up" (`setup = "quick"` in `me/settings.toml` until then).
- **"I want a new coach", in any words, at any point,** runs the `coach` skill (`.claude/skills/coach/SKILL.md`): for a web coach, keys, describe (a narrative file), audition across every keyed service, approve and name, the stable; the quick coach is one question, then that audition. Local coaches keep takes and a clip until the local redesign.
- **A request from outside a copy of this repo** ("use https://github.com/RNCDev/sweatcast and set me up") follows the README's "For Claude" section: download to `~/sweatcast` (git or the ZIP; no GitHub account needed), then hand over to a session opened in that folder, where these instructions and the safety settings load. A new listener is set up only on their own computer, never on Claude Code on the web; one already set up, with their private context repo attached, keeps working there with web coaches. Keep that section, the README's Start here and the setup skill in step.

Rules that always hold:
- **Never read, print or copy `me/.env`**: it holds the listener's voice keys, pasted into that file by the listener, never into the chat. Only the engine reads it, when it sends to a voice service.
- **During a session, write only inside `me/`.** Never put personal details (health, location, the log, drafts) in the engine, its tests or its examples; the pre-push hook in `tools/hooks/` and CI both refuse them.

## Two assistants

sweatcast runs under Claude Code and under ChatGPT's Codex (Codex in the ChatGPT desktop app, the Codex CLI or an editor), on the listener's own computer.
- **Claude Code's files are the source:** this file, `.claude/skills/` and `.claude/settings.json` (which allows `./sweatcast` and denies Claude's file reads of `me/.env`). Skills name Claude Code's tools.
- **Codex reads `AGENTS.md` and `.agents/skills/`,** both written by `./sweatcast harness sync` (`tools/harness.py`). `AGENTS.md` sends Codex here and says what to use in place of each Claude Code tool (a numbered question for AskUserQuestion, `./sweatcast show` for SendUserFile, research done in turn for background agents). `.agents/skills/<name>/` is an exact copy of `.claude/skills/<name>/`; the ChatGPT app's own import of Claude skills makes the same copy, so it changes nothing. **After editing a skill, run `./sweatcast harness sync`**; the tests fail until it's done.
- **`.codex/config.toml`** turns on the sandbox's network, and **`.codex/rules/sweatcast.rules`** lets `./sweatcast` run outside Codex's sandbox, as `.claude/settings.json` allows it here; Codex reads both once the listener trusts the folder. The harness check keeps that rule and the allow list naming the same command.
- **Without the rule** (an untrusted folder), Codex's sandbox hides the GPU, uv's home cache, git's settings and the network. So inside it (`CODEX_SANDBOX` set) `./sweatcast` keeps uv's cache in `.cache/uv` (git-ignored) and a local render that can't see the GPU says to run again outside the sandbox; and setup skips the privacy hook, with the reason, whenever git's settings can't be written.
- **The key:** Claude Code's settings deny its file tools `me/.env`, and both assistants are told never to read it (a shell command could). A system-level block in Codex (a permission profile denying `**/*.env`) also stops the engine reading it, so web coaches couldn't speak.
- Tried end to end on 2026-10-25 with the Codex CLI the ChatGPT app ships (0.164), on the Free plan's model: setup and a ten-minute workout with Coach Andy. The app's own trust prompt, multiple-choice questions and approval prompts weren't tried by hand.

## Three layers

1. **Engine** (this repo, public, versioned): `sweatcast`, `tools/`, `.claude/`, `AGENTS.md`, `.agents/`, `.codex/`, `tests/`, the shared knowledge in `knowledge/`, the template `me.example/`, and `docs/`.
2. **Coaches** belong to the listener. Each is a persona folder in `me/personas/` (a person's name, how they talk, how they sound; `knowledge/voices.md`), of one of two kinds: a **web coach** (`kind = "web"`), an original voice a web service designed from the listener's description and saved in their own account, which speaks only through that service; or a **local coach** (`kind = "local"`), a ten-second clip every local engine copies, which renders only locally. Five stand-ins ship in the template, all `placeholder = true`, so a build with no coach named picks the listener's own coach before them:
   - **Coach Andy** (`me.example/personas/coach-andy-local/`), the local stand-in: sweatcast 8's public Chatterbox Coach clip with its measured pace, and a short test clip, `sample.mp3`, that setup plays first.
   - **Four default web coaches** from one description: Coach Reed (Fish Audio), Coach Ellis (ElevenLabs), Coach Nolan (Gemini) and Coach Owen (Inworld), each `pending = "design"`: setup's quick start, or else the first build that needs one, designs and saves its voice, saying so first.
   Local model weights never go in git: they download into `models/` (git-ignored, at pinned revisions). A sweatcast 8 folder's shipped clips come from the `v8.0.1` git tag (a git clone, not a ZIP) for `./sweatcast migrate`.
3. **The listener's context** (private): `me/`, ignored by git, holds everything about one person; `me.example/` is its template. Set `SWEATCAST_HOME` to keep it elsewhere. Every tool reads its paths from `tools/paths.py`, and reads and writes the context files only through `tools/context.py`. Each Markdown context file opens with a TOML block between `+++` lines naming its format (`schema = 6`) and holding the settings the tools read; `settings.toml` is plain TOML. The profile is four files, which `context.profile()` reads as one. `./sweatcast migrate` brings a folder from an older release up to date.

## The listener's files (`me/`)

- **The profile, in four files** by how often each part changes and who reads it. `context.profile()` merges their settings and joins their prose, so a setting counts in any of them, but each has a home (`SETTING_HOMES` in `tools/context.py`), where setup writes it and `migrate` moves it; the home file wins, and `check` notes a setting written twice.
  - `profile.md`, who the listener is (rarely changes; every workout reads it): `name` (what the coach calls them), `experience`; the Basics (neighborhood), Listening setup and other prose.
  - `training.md`, how they train (changes with new gear or check-in feedback; every workout reads it): `likes`, `dislikes`, `[[kits]]` (with optional `weights` and `unit`); the Default session section, and Equipment kits notes the settings can't hold.
  - `content.md`, what fills the rests (changes most; only research and the story tools read it): `youtube_favorites`, `puzzles`, `[[interests]]` (name, slot, detail), `[[feeds]]`; the Content (with "Never bring up") and Taste sections.
  - `settings.toml`, the tools' own settings (plain TOML, no prose; setup writes them): `setup` (`"quick"` until the second half of setup), `render` (the audio routes in order, default `["local"]`; a web coach always speaks through its own service and a local coach always renders locally, so it matters only with no coach to go by), `cloud_max_chars` (a web build's ceiling), `deliver_to` (a folder, or a list of them, one per computer), `words_per_minute` (a rough rate `./sweatcast get wpm` prints; builds use each coach's measured pace).
- `health.md`: injuries and limitations. Its `+++` block holds a `[[limits]]` row per injury (area, side, level `off-limits` or `delicate`, optional `flags` and `rehab`, note), which `./sweatcast brief` applies; the prose holds each injury's story and the `## Clinician rules`, followed literally. The check-in loosens or tightens a limit.
- `log.md`: the session log (added only with `./sweatcast log-session`, which checks every field) and the listener's feedback ("too long", "loved that topic") under Feedback.
- `workouts/`: one folder per workout, `<stem>/` (such as `2026-10-25-strength-25/`): the `@@`-marked draft (`<stem>.draft.txt`), the brief it was designed from (`<stem>.brief.md`), the menu the build checks (`<stem>.menu.json`), and the build's `<name>.txt` and `<name>.build.json` (with the MP3 until it's delivered, or the web copy on the web). `checks/` holds smoke tests and builds of drafts outside a workout folder (`tools/workouts.py` decides). `research/` holds the filler: `daily/` (each day's research sheet and feeds), `videos/` (video deep-dive sheets and transcripts), `puzzles/`, `reserve/` (evergreen pieces researched ahead of time; `pantry/` before 10.2.0, still read) and `told.jsonl` (every filler item told). `.audio-cache/` holds rendered clips (`./sweatcast cache prune` clears old ones freely), and `.logs/` each build's render log and `builds.jsonl`, one record per MP3.
- `personas/<slug>/`: one folder per coach, named for the coach and where they speak (`coach-maya-fish`, `coach-andy-local`; a folder from before 10.3.0 keeps its name, and lookup by the plain `coach-maya` still finds it). `persona.md` (persona schema 5) has a `+++` block: `name`, `aliases`, `kind`, `placeholder`, `description`; a web coach's `service`, `voice_id`, optional `model`, `style` (kept empty: Gemini takes none yet), `made`, `pending = "design"` on an unmade default, `[voice]` (who, sound, energy, pace, avoid: what services design from) and `[character]` (what the script writer follows); a local coach's `[local] engine`. Below it, free notes, or a local coach's `## How this coach talks`; the brief quotes `[character]` and the prose's `- Label: text` lines. `pace.json` holds pace per engine or service, model and voice (a web coach's starts as an estimate from its sample) and each computer's render speed. A web coach adds `sample.mp3` (its approved candidate); a local coach `clip.wav`, `clip.txt` (the sound and its words) and `takes/` (Coach Andy also ships a `sample.mp3`, his test clip). `personas/.auditions/<date>-<n>/` holds an audition in progress (each candidate's WAV and MP3, `narrative.md`, `candidates.json`); `personas/.archive/` holds archived coaches, out of the list but found by name for old log lines.
- `.env`: the web voice keys (`FISH_AUDIO_API_KEY`, `ELEVENLABS_API_KEY`, `GEMINI_API_KEY`, `INWORLD_API_KEY`), one `NAME=value` per line, made by `./sweatcast keys init <service>`, opened in the system's editor by `./sweatcast keys open`, filled in by the listener.
- `movements.toml` (optional): private `[[movement]]` entries in the catalog's format, loaded after the shipped ones (a shipped id wins).
- `.gitignore`: for keeping `me/` as its own private git repo, nested in the engine's folder and ignored by the engine's git (never a submodule). It leaves out `.env`, the clip cache, MP3s (keeping each web coach's `sample.mp3` and a workout's web copy), render logs, designed takes and auditions in progress. `./sweatcast backup` commits and pushes that repo, and refuses to commit a `.env` even if the rule is missing.

## Knowledge (`knowledge/`)

- `movements.toml`: the movement catalog. Each movement's equipment, patterns, muscles, how much it loads each joint area (`loads` 0 to 3, and `support` for the resting side), flags, intensity, level, `effort` (easy, moderate or hard, on every conditioning movement), timing, spoken setup and cues, and the coaching a listener without a mirror needs (`rep`, `feel`, `faults`); also the fixed lists of equipment, patterns, muscles, areas and flags, the kit presets, and `[limit_cues]` (spoken cues per area and limit level). Read only through `tools/catalog.py`.
- `sessions.toml`: the session methods (goals, length, levels, how warm-up, work, finisher and cool-down share the time, the patterns that fill each block), the doses per intensity and level, the all-out sprint rule (`[all_out]`: rest at least four times the work), the caps on hard sets and efforts per session, and the bodyweight reps above novice; every number marked as sourced or a house default. Read only through `tools/sessions.py`.
- `programming.md`: how to set effort, rest, tempo and progression, and how the check-in's readiness changes the day, with sources; `sessions.toml` takes its numbers from it.
- `injury-playbook.md`, `kits.md`: what off-limits and delicate mean for each area, the signs that let a limit loosen, and the red flags that stop a session; what each kit usually holds and how to script around it. Where they disagree with `me/health.md`, the strictest wins.
- `script.md`: what goes in a script, from the welcome to the sign-off (the `movements:` line and segments, timed work, the opening and its safety rules, coaching from the notes and limit cues, the self-check that adjusts each main movement, filler, the quiz and deep dive, the close). `tts-rules.md`: how to write for text-to-speech, and how the coach should sound.
- `content.toml`: the filler plan: the slots (today, science, deep dive, quiz, delight, learn), how many a session carries by length, the reserve's target per evergreen slot, the default categories. Read only through `tools/content.py`.
- `voices.md`: the two kinds of coach and the stand-ins, how a web coach is made, the web services with their costs, terms and what goes to them, the local engines by computer and how a local coach is made, pace, and what was tried. `services.toml`: each web service's address, key name, default model, rates (with the date checked), `design_usd` where published, concurrency, request limit, `note` and `tried_live`; read only through `tools/cloud.py`.
- `smoke-test.draft.txt`: a one-minute check that also measures a local coach's pace on a route.

## Tools

Every tool runs through `./sweatcast <command>` (`tools/sweatcast.py` dispatches; `./sweatcast help` lists the commands, and each Python tool takes `--help`; `setup` and `doctor` are shell scripts that run on any arguments), in the project's environment (`.venv`, Python 3.11), or under `SWEATCAST_PYTHON` if set; the Mac's own `python3` is never used. Skills and docs call tools only this way, so one permission rule covers them. Exit codes (`tools/cli.py`): 0 done; 1 issues to fix; 2 the total ran more than three percent off plan; 3 a local coach isn't measured on this route yet; 4 a web service refused the key, payment or quota; 64 the command was wrong (an unknown option or coach, a missing draft) or a web coach can't speak here (no key for its service on this computer, or `--engine` naming another service).

**Setup and the computer**
- `tools/doctor.sh` (`doctor`): the readiness check, a shell script so it runs before the environment exists: the system, chip, graphics, memory and free disk; uv, git, ffmpeg and the environment; whether local voices work here and, if not, why; then `tools/doctor.py`'s lines (the models on disk, `me/` and its schema, each `deliver_to` folder, ffmpeg's MP3 and loudness abilities). `--facts` prints `key=value` lines that `doctor.py`'s `facts()` reads, so the shell script alone decides what a computer can do; `SWEATCAST_FAKE_*` variables stand in for the hardware in tests. On Claude Code on the web (`CLAUDE_CODE_REMOTE=true`) local voices are off, and `doctor.py` adds what the web needs: the key as an environment setting, the hosts to allow, and whether the context folder is kept.
- `tools/setup.sh` (`setup`): one-time setup, safe to rerun: the readiness check, uv (`--install-uv` runs Astral's installer), the environment (`uv sync`), `me/` from `me.example/` (or a migration of an existing one, adding its `.gitignore` if missing), the privacy hook (skipped, with the reason, outside a git checkout or where git's settings can't be written), and where local voices run, the local engine (an optional uv extra: MLX on Apple Silicon, CUDA PyTorch with an NVIDIA card, processor PyTorch without one, remembered in `.venv/.sweatcast-extra`) and the coaches' local model. `--local` insists, `--all` fetches every local model, `--no-models` stops at the base environment; a profile whose `render` list leaves out local gets no engine.
- `tools/models.py` (`models`): the models in `models/`, and `adopt` from Hugging Face's usual cache. `tools/voices.py`: the local models' pins (`LOCAL_MODELS`, `ENGINE_EXTRAS`, `VOICE_DESIGN`), pace and render speed per coach, and downloads. `tools/ffmpeg.py` finds ffmpeg (PATH, else imageio-ffmpeg's copy). `tools/paths.py`: where everything lives (the context folder from `SWEATCAST_HOME`, else `me/`, else on Claude Code on the web the one folder beside the engine holding a profile and `personas/`). `tools/harness.py` (`harness`, `sync`): Two assistants, above.

**Building a workout**
- `tools/build.py` (`build <draft> "<name>"`): draft to `.txt` and `.mp3` in one step (the lint, then the render) into the draft's workout folder (else `checks/`), then a copy of the MP3 to the profile's `deliver_to` folder, after which the local MP3 is removed (a failed copy or no folder keeps it; the build record says which, under `delivered_to`, `kept_local` and `reason`).
  - The lint needs the draft's menu (`<stem>.menu.json`, from `brief --save`) and stops on a movement that isn't on it, whatever `--force` says; only the smoke test builds without one.
  - `--coach` names the coach (`--voice`, the old name; default the one used last, else the listener's own, else a stand-in that can speak here; it stops when the one used last is archived) and `--engine` the route; the build resolves both and passes them to the lint and the render. A `pending` default web coach is made first (`coaches make`), except with `--lint-only`.
  - `--lint-only` stops after the lint. `--follow` renders ahead while a draft is being written, keeping the model loaded and rendering each new or edited paragraph as it lands, and steps aside when the full build starts; `--clips-only` renders what the draft holds once; both are local only (refused for a web coach, where each re-render is billed). `--allow-estimated` renders with a local coach not yet measured on the route.
  - `--web` (on by default on Claude Code on the web, where it replaces the copy) makes the web copy with `tools/webcopy.py`: the MP3 mono at 48 kbps in parts of at most 14 MB (`<name>.web-1.mp3`...) and `<name>.player.html`, which plays them in order; the workout skill publishes it as an artifact and the backup commits it.
- `tools/draft.py`: the draft format (the `movements:` line, never spoken, then `@@ <seconds> | <label>` segments, `[pause]`, `[chime]`, `[hold]`), where a draft's brief and menu sit, and the timing layout the lint and the render share. `tools/tts_build.py` (`lint`): the lint and `.txt` export; it stops on what must hold (text a voice can read cleanly, paragraphs short enough for one clip, the total within three percent, the menu check), and shows segments far off their slots (`--strict` makes those count) and each held segment's spare silence. `tools/menu.py`: the menu file and the build's check (a declared movement off the menu, a catalog movement named in the text that's off it, nothing declared, segments that don't add up; a menu movement named but not declared is a warning).
- `tools/render.py` (`render`; `build` runs it): voices each paragraph, with the clip cache, loudness pass, chimes and end tone, one render at a time (`tools/locks.py`, flock on a Mac and msvcrt on Windows, shared with the pace file), and a record of each build. `tools/engines.py`: the local engines and the voice designer, and everything that depends on mlx-audio's or huggingface_hub's internals. `tools/cache.py` (`cache`): the clip cache's size, and `prune`.
- `tools/player.py`: plays a take with the system's player; `show <file>` opens a file's folder with it selected (Finder or Explorer; on Linux, the folder), the fallback when an MP3 can't be sent into the chat.

**Coaches and voices**
- `tools/personas.py`: lookup by folder name, name or alias (the archive only when asked, as for names read from the log), the one used last, the default a build takes, `archive`, `voice_description` (the `[voice]` table as the line a service designs from), `web_key` (a web coach's identity for cache and pace) and `voice_for(coach, route)`, the voice dict the lint, render and engines take.
- `tools/coaches.py` (`coaches`, `voices` its old name): the list (where each speaks, the stand-ins, the ones made the first time they're used), `last`, `measured`. For web coaches: `audition <narrative> [--services] [--coach] [--play]` (candidates from every keyed service, lettered; nothing saved but Gemini's), `keep <audition>/<letter> --name [--replace-old]` (saved at the service as "sweatcast <name>", the coach written with `sample.mp3` and a pace estimate), `forget-audition`, `make` (a pending default), `archive`. For local coaches: `design` (takes from the local Qwen3 VoiceDesign on a Mac), `keep` (a take or a brought clip, converted to 24 kHz mono), `set`, `download`.
- `tools/routes.py`: the routes (local, fish, elevenlabs, gemini, inworld), which work here (the readiness check's verdict and the installed engine; a key in `me/.env` or the environment), and which a build takes: a web coach's own service, a local coach `local`, and with neither the first route in the profile's `render` list that works. `tools/keys.py` (`keys`): which services have a key (never the key), `init`, and `open` (the file in the system's editor, never read).
- `tools/cloud.py`: the web engines' core (`knowledge/services.toml`, HTTP with retries, errors sorted into what the listener must fix, WAV and resampling without numpy, the cost estimate, `voice_for` a web coach), with one module per service in `tools/services/` (`fish`, `elevenlabs`, `gemini`, `inworld`), each with `design`, `save`, `delete` and `speaker` (ElevenLabs with neighbors and a seed, Inworld with the previous paragraph). `tools/char_weight.py`: OmniVoice's character-weight rule (Apache 2.0, vendored); every measured pace counts in it.

**The listener's context**
- `tools/context.py`: the one reader and writer of the context files: the schema check, the profile's settings (`get coach | route | routes | wpm | experience`, `deliver`), coaches' `persona.md` files, `log-session` (a checked session line; with `--draft`, its movements are the draft's `movements:` line) and `check`, which lists anything still to fill in (template `[hint]` lines, feeds, the experience level, a `[[limits]]` row for each injury, a coach) and anything the tools can't read or don't know (likes, kit equipment, flags or rehab ids not in the catalog, a route that isn't one, a coach with no voice or clip, a fault in `me/movements.toml`).
- `tools/migrate.py` (`migrate`): brings an older context folder up to the current schema, backing it up first (never `.env`). Coach files carry their own schema; 4 to 5 there (10.0.0) adds `kind = "local"` to every coach, archived ones too, and the `me/.gitignore` rules for coaches' samples, made voices and auditions. For the context files, 5 to 6 (12.0.0) splits `profile.md` into the four profile files by `SETTING_HOMES` and `PROSE_HOMES`, backing up any part already there before writing it; 4 to 5 moves the workouts into a folder each (and `checks/`, `research/daily/`), never overwriting; 3 to 4 turns the profile's `[[voices]]` into coaches (Chatterbox Coach becomes Coach Julius and Qwen3 Coach becomes Coach Solo, old names kept as aliases), with cached clips still valid. `tools/workouts.py`: the folder-per-workout layout (`out_dir` for a build, and `reorganize` for that migration).
- `tools/backup.py` (`backup`, `-m <message>`, `--no-push`): commits everything in the context folder and pushes it, when the folder is the top of its own git repo; otherwise it prints how to make one and changes nothing. It refuses a remote GitHub reports as public. The workout skill runs it last.

**Planning and research**
- `tools/brief.py` (`brief --goal --minutes --kit|--preset|--equipment`, optional `--level`, `--target`, `--limit area=level[:side]`, `--avoid`, `--coach`, `--save <draft path>`, `--today`): today's ingredients, in Markdown: the listener and their coach (the coach's `[character]` and the pace to write to), how today fits the week, today's limits (what each means, the clinician's rules, the limit cues with the side filled in, the playbook's paragraph per area, the red flags), the safe menu (every movement the kit, level, limits, `Avoid:` lines and dislikes allow, by primary pattern, each with its facts, its load on today's limited areas and its coaching notes), the weights on hand, the programming guide and the kit's notes. It plans nothing; `--save` writes `<stem>.brief.md` and `<stem>.menu.json` beside the draft.
- `tools/screen.py`: the safety screen behind the menu (the request, the limits, `Avoid:` lines and dislikes; the limit cues; the equipment that would open up more movements). `tools/catalog.py`: loads and checks the catalog (plus private movements), matches a logged name to a movement, and selects what a kit, level and limits allow. `tools/movements.py` (`movements`): browses what a kit allows by pattern (`--preset` or `--equipment`, `--level`, `--pattern`, `--avoid`); `--about <ids>` prints a movement's coaching notes. `tools/sessions.py`: loads and checks `sessions.toml`. The old composer (`./sweatcast session`) was retired in 7.2.0; the eval runs it from the v7.1.0 tag as its baseline.
- `tools/coverage.py` (`coverage`): from the log, the patterns the last session left out and those the last seven days neglected, the movements to avoid, the last format and each movement's last load, the days since the last session, the sessions this week and the latest feedback.
- `tools/feeds.py` (`feeds`): fetches `content.md`'s `[[feeds]]` (team results and schedules, weather, local, science and taste headlines, weekly podcasts and puzzles, on this day, Wikipedia's featured article, most read, in the news and did you know) into `me/workouts/research/daily/<date>-feeds.md`, and prints only the weather.
- `tools/content.py` (`content`): `plan --minutes N` (what the rests carry: each slot's count and the categories due, everything told in the last thirty days, the reserve's unused pieces and what to restock); `log` (one `--item "slot | category | title [| source [| reserve slug]]"` per item told); `reserve` (`pantry` its old name). The research templates are in `.claude/skills/workout/research.md`.
- `tools/youtube.py` (`youtube`): `pick` (recent unused videos from `content.md`'s favorites, and any series in progress), `transcript`, `done` (a series part told), and `puzzles` (recent puzzle videos not yet used).

**Privacy**
- `tools/hooks/`: the pre-push hook, `check-private.sh` (checks every commit in a range; the hook and CI both use it) and `private-paths`, the one list of paths never to push.

## Tests

`tests/` holds fast checks with no models, network or personal files; run `./sweatcast test` after changing a tool (CI runs them on every push, with Python 3.11). The largest suite, `tests/test_tools.py`, covers the lint, timing layout, build exit codes and record, render lock, context files, log, migration, coverage, feed parsers, YouTube series, `./sweatcast`, the privacy hook, and a fresh copy running on `me.example/`. The rest, by subject: `test_brief.py` (the brief, menu check and `movements:` line), `test_catalog.py` (the catalog and filter, with `tests/fixtures/movements.toml`), `test_sessions.py`, `test_screen.py`, `test_content.py` (the filler plan, record and reserve), `test_personas.py` (coaches, design, pace, auditions, keep and make), `test_cloud.py` (the web engines and web rendering; both against local fake servers, `tests/fakes.py`), `test_routes.py`, `test_keys.py`, `test_models.py`, `test_setup.py` (setup and the readiness check on faked computers, and Claude Code on the web), `test_migrate4.py` (from an invented v8 folder, with the v8 clips from the `v8.0.1` tag via `tests/v8.py`), `test_migrate5.py`, `test_migrate6.py` (the profile's split, against the 11.x template in `tests/fixtures/profile-5.md`, and the merge rules), `test_webcopy.py`, `test_backup.py` (local repos only) and `test_harness.py` (the two assistants' files); fixtures are in `tests/fixtures/`.

Also in the engine: `pyproject.toml`, `uv.lock`, `.python-version` (the pinned environment); `docs/research/` (the research `sessions.toml` cites); `docs/eval/` (the judged eval grid behind each release: `cases.toml` and `extra-cases.toml`, the invented listeners, `briefs.sh` and `skeletons.sh`, the writer's and judge's briefs, a results file per run); `VERSION` and `CHANGELOG.md`.

## Audio

`tools/render.py` voices each paragraph on the route the build picked.
- **A web coach** speaks through its own service with the listener's key, by the voice saved there (`tools/cloud.py`); no clip is sent. A web build sends once, at the end, a few requests at a time, after printing the characters and approximate cost and checking `cloud_max_chars`. Its pace starts as an estimate from its sample, so it needs no smoke test.
- **A local coach's clip** is cloned locally: Chatterbox Turbo or Qwen3-TTS through `mlx-audio` on an Apple Silicon Mac, or Chatterbox Turbo through Resemble AI's PyTorch `chatterbox-tts` on Windows or Linux (CUDA with an NVIDIA card; the processor without one, experimental). Qwen3 and local voice design are Mac-only. On an M3 with 16 GB, Chatterbox Turbo renders at about 0.7 times the length of the speech (a 30-minute workout in about 20 minutes) and Qwen3 at about 1.3 to 1.45; on an RTX 2080 Super, Chatterbox Turbo at about 0.5. Turbo keeps the GPU busy, so a local render or voice design holds a lock and a second one waits; `--follow` overlaps rendering with writing. Model sizes in `models/`: about 3.3 GB for Chatterbox Turbo, 4.2 GB for Qwen3, 4.5 GB for the voice designer, 4 GB for Chatterbox Turbo on PyTorch; keep only the ones a coach in use needs.
- Every engine returns `say(text, seed)` with 16-bit mono PCM at 24 kHz, so the cache, loudness pass, timing layout and build record don't know which spoke. The cache key holds a local coach's clip, engine, model, settings and runtime, or a web coach's identity (service, voice ID, model, style, settings), never a key or a name.
- On Windows, `./sweatcast` runs from Git Bash and the venv's Python is `.venv/Scripts/python.exe`. On Claude Code on the web only web coaches speak: the key is an environment variable in the cloud environment's settings (the tools read the environment before `me/.env`), and the service's host (`api.fish.audio`, `api.elevenlabs.io`, `generativelanguage.googleapis.com`, `api.inworld.ai`) goes on its network allowlist.

## Releases

Versions follow Semantic Versioning, tracked in `VERSION`, `pyproject.toml` and `uv.lock` (the `sweatcast` package's version line), and `CHANGELOG.md`, tagged `vX.Y.Z` on GitHub (RNCDev/sweatcast). The maintainer decides the level:
- **Major:** a change that breaks how existing drafts, coaches, commands or the `me/` layout work, so something has to be migrated, or a change as large as a new assistant to run under (11.0.0). Its CHANGELOG section says what to do under "For forks". A change to a context file's format raises `SCHEMA` in `tools/context.py` and adds a step to `tools/migrate.py`, so a fork migrates with one command (`./sweatcast migrate`, which `./sweatcast setup` also runs).
- **Minor:** a new capability, such as an engine, a web voice service, a skill step or a tool option.
- **Patch:** fixes, tuning and doc corrections.

Listener content lives in `me/` and is never part of the engine's git. When a set of changes is finished and working, release it: a dated section in `CHANGELOG.md`, the version bumped, commit, tag (`git tag -a vX.Y.Z -m "..."`), push with tags, and a GitHub release (`gh release create vX.Y.Z --notes-file <that section>`). Ask before pushing if it's unclear whether the work is done.
