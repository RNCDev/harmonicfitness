# sweatcast: a workout podcast, made fresh each session

sweatcast turns a request for a workout into a narrated MP3 for earbuds, with no screen and no timer. The audio is the workout: it tells the listener what to do, keeps them company, and moves them along on time. The lint predicts each segment's spoken length for the chosen coach, and the render lays segments on the plan's clock: a segment with time to spare breathes a little between paragraphs, then ends early rather than going quiet, unless a `[hold]` keeps it its full length for timed work. Only the total is held to plan, within three percent either way; a natural, human voice matters more than exact timing.

Priorities, in order: safe for the listener's body today, clean to the ear, worth listening to.

**Any request for a workout, in any words, runs the `workout` skill** (`.claude/skills/workout/SKILL.md`). It covers check-in (asked first, from the profile, health and log alone), research, the brief, design, script, build, log and backup: `./sweatcast brief` supplies the ingredients (the listener, today's limits, the safe menu with coaching notes, the programming guide), the writer designs the session and writes it, and the build refuses any movement the menu doesn't hold. **A request to get started ("set up sweatcast", "set me up", "finish setting me up"), or to change the listener's profile, injuries, feeds, audio route or delivery runs the `setup` skill** (`.claude/skills/setup/SKILL.md`), and so does a workout request when `me/profile.md` doesn't exist yet. Setup's quick start asks one round of questions, uses Coach Demo and ends with a ten-minute workout; the rest of the interview waits for "finish setting me up" (the profile says `setup = "quick"` until then). **"I want a new coach", in any words and at any point, runs the `coach` skill** (`.claude/skills/coach/SKILL.md`): the quick coach (one question, one take) or the full path (name, description, takes, keep one). Claude never reads, prints or copies `me/.env`; a key is pasted into that file by the listener, never into the chat.

## Three layers

1. **Engine** (this repo, public, versioned): `tools/`, `.claude/skills/`, `tests/`, and the shared knowledge in `knowledge/`.
2. **Coaches** belong to the listener, not the engine. One stand-in ships in the template, Coach Demo (`me.example/personas/coach-demo/`: sweatcast 8's public Chatterbox Coach clip with its measured pace, `placeholder = true`), so a new listener renders at once; a build picks any other coach before it. Each is a persona folder in `me/personas/` (a person's name, how they talk, a ten-second clip every engine copies; `knowledge/voices.md`). Local model weights never go in git: they download into `models/` (git-ignored, at pinned revisions), and cloud voices take the listener's own key from `me/.env`, which nothing but the engine reads. `tools/migrate-assets/v8-voices/` keeps the clips sweatcast 8 shipped, for `./sweatcast migrate`, until 10.0.0.
3. **The listener's context** (private): `me/`, ignored by git, holds everything about one person. `me.example/` is its template. Set `SWEATCAST_HOME` to keep it elsewhere; every tool reads its paths from `tools/paths.py`, and reads and writes the context files only through `tools/context.py`. Each context file opens with a TOML block between `+++` lines naming its format (`schema = 5`); in `me/profile.md` that block also holds every setting a tool reads. A folder from an older release is brought up to date by `./sweatcast migrate`.

During a session, write only inside `me/`. Never put personal details (health, location, the log, drafts) in the engine, its tests or its examples; the pre-push hook in `tools/hooks/` and CI both refuse them.

## Files
- `me/profile.md`: stable facts about the listener. The `+++` block at the top holds the settings the tools read (`render`, the audio routes in order of preference, and `cloud_max_chars`, a cloud build's ceiling; `deliver_to` (a folder, or a list of them, one per computer), `words_per_minute` (the rate `./sweatcast lint` assumes with no coach), `name` (what the coach calls the listener), `experience`, `likes` and `dislikes`, `youtube_favorites`, `puzzles`, `[[kits]]` (with optional `weights` and `unit`), `[[interests]]` (what the filler rotates through: name, slot, detail), `[[feeds]]`); the prose below holds the rest (basics, equipment kits, interests, `## Taste` (favorite shows, books, music, food and drink, rated), tone). Update it when something lasting changes.
- `me/health.md`: injuries and limitations. Its `+++` block holds a `[[limits]]` row per injury (area, side, level `off-limits` or `delicate`, optional `flags` and `rehab`, note), which `./sweatcast brief` applies; the prose holds each injury's story and the `## Clinician rules`, followed literally. The check-in loosens or tightens a limit.
- `me/log.md`: session log and the listener's feedback. Sessions are added with `./sweatcast log-session`, which checks every field; feedback given at any time ("too long", "loved that topic") goes under Feedback.
- `me/workouts/`: one folder per workout, `<stem>/` (such as `2026-10-25-strength-25/`), holding the `@@`-marked draft (`<stem>.draft.txt`), the brief it was designed from (`<stem>.brief.md`), the menu the build checks it against (`<stem>.menu.json`), and the build's `<name>.txt` and `<name>.build.json` (and the MP3 until delivered, or on the web its web copy); `checks/` holds smoke tests and builds of drafts outside a workout folder (`tools/workouts.py` decides); `research/` holds filler fact sheets (`daily/` each day's research sheet and feeds, `videos/` the video deep-dive sheets and transcripts, `puzzles/` older quiz puzzles, `pantry/` evergreen pieces researched ahead of time, and `told.jsonl`, the record of every filler item told), `.audio-cache/` holds rendered clips (prune them freely with `./sweatcast cache prune`; each coach's measured pace is in its own folder), and `.logs/` holds each build's render log and `builds.jsonl`, one record per MP3 (each MP3 also gets a `<name>.build.json` beside it).
- `me/.gitignore`: for keeping `me/` as its own private git repo (nested in the engine's folder, ignored by the engine's git, never a submodule): it leaves out `.env` (API keys), the clip cache, MP3s, render logs and designed takes. `./sweatcast backup` commits and pushes that repo, and refuses to commit a `.env` even if the rule is missing.
- `me/personas/<slug>/`: one folder per coach: `persona.md` (a `+++` settings block: name, aliases, description, one table per engine such as `[local] engine` or `[deepgram] voice`; then `## How this coach talks`, which the brief quotes), `clip.wav` and `clip.txt` (the sound and its words), `pace.json` (measured pace per engine and model, and each computer's render speed), `services.json` (voice IDs a cloud service made from the clip) and `takes/`. Read and written through `tools/context.py` and `tools/personas.py`.
- `me/.env`: cloud voice API keys, one `NAME=value` per line, made by `./sweatcast keys init <service>` and filled in by the listener. Never read, printed or copied by Claude (`.claude/settings.json` denies it); only the cloud engine reads it, when it sends.
- `me/movements.toml` (optional): private `[[movement]]` entries in the catalog's format, loaded after the shipped ones (a shipped id wins); `./sweatcast check` lists any problem in them.
- `knowledge/content.toml`: the filler plan: the slots (today, science, deep dive, quiz, delight, learn), how many of each a session carries by length, the pantry's target per evergreen slot, and the default categories. Read only through `tools/content.py`.
- `knowledge/script.md`: what goes in a script, from the welcome to the sign-off: the draft's `movements:` line and segments, timed work, the opening and its safety rules, coaching each movement from its notes and limit cues, the self-check that adjusts each main movement as the session goes, filler, the quiz and deep dive, and the close.
- `knowledge/tts-rules.md`: how to write for text-to-speech, and how the coach should sound.
- `knowledge/voices.md`: coaches and how they're made, the routes (local engines, by computer, and the cloud services with their costs and what goes to them), pace, and what was tried.
- `knowledge/movements.toml`: the movement catalog, every movement a session can use with its equipment, patterns, muscles, how much it loads each joint area (`loads` 0 to 3, and `support` for the resting side), flags, intensity, level, `effort` (easy, moderate or hard, on every conditioning movement), timing, spoken setup and cues, and the coaching a listener without a mirror needs (`rep`, `feel`, `faults`); also the fixed lists of equipment, patterns, muscles, areas and flags, the kit presets, and `[limit_cues]` (spoken cue lines per area and limit level, printed when that limit is active). Read only through `tools/catalog.py`.
- `knowledge/sessions.toml`: the session methods (goals, length, levels, how warm-up, work, finisher and cool-down share the time, the patterns that fill each block) and the dose ranges per intensity and level, the all-out sprint rule (`[all_out]`: rest at least four times the work), (with the caps on hard sets and efforts per session and the bodyweight reps above novice), every number marked as sourced or a house default. Read only through `tools/sessions.py`.
- `knowledge/programming.md`: how to set effort, rest, tempo and progression, and how the check-in's readiness changes the day, with its sources; `sessions.toml` takes its numbers from it.
- `knowledge/injury-playbook.md`, `knowledge/kits.md`: programming references. The playbook says what off limits and delicate mean for each area, the signs that let a limit loosen, and the red flags that stop a session; `kits.md` says what each kit usually holds and how to script around it. Where they disagree with `me/health.md`, the strictest wins, and anything health.md bans is out.
- `knowledge/smoke-test.draft.txt`: a one-minute check that also measures a coach's pace on a route. `knowledge/services.toml`: the cloud voice services (address, key name, default model, rates per million characters or bytes with the date checked, concurrency, request limit, how the clip travels, `tried_live`), read only through `tools/cloud.py`.
- `sweatcast` (repo root): the one command. `./sweatcast <command>` runs each tool in the project's environment (`.venv`, Python 3.11); `./sweatcast help` lists the commands. Its implementation is `tools/sweatcast.py`, and `./sweatcast setup` runs `tools/setup.sh`, which makes the environment, so it needs no Python first. Skills and docs call tools only through it, so one permission rule covers them.
- `tools/doctor.sh` (`./sweatcast doctor`): the readiness check, a shell script so it runs before the environment exists: the system, chip, graphics, memory and free disk; uv, git, ffmpeg and the environment; whether local voices work here and, when not, why; then `tools/doctor.py`'s lines (the voice models on disk, `me/` and its schema, each `deliver_to` folder there or not, ffmpeg's MP3 and loudness abilities). `--facts` prints `key=value` lines, which `doctor.py`'s `facts()` reads, so the shell script is the one place that decides what a computer can do; `SWEATCAST_FAKE_*` variables stand in for the hardware in tests. On Claude Code on the web (`CLAUDE_CODE_REMOTE=true`) local voices are off whatever the hardware, and `doctor.py` adds what the web needs: the key as an environment setting, the hosts to allow, and whether the context folder is kept (its own repo with a remote) or this is a one-time session. `tools/ffmpeg.py` finds ffmpeg (PATH, else imageio-ffmpeg's copy in the environment); `tools/player.py` plays a take with the system's player.
- `tools/setup.sh` (`./sweatcast setup`): one-time setup, safe to rerun: the readiness check, uv (`--install-uv` runs Astral's installer), the Python environment (`uv sync` into `.venv`), `me/` from `me.example/` (or a migration of an existing one, adding its `.gitignore` if it has none), the pre-push hook (skipped, with the reason, outside a git checkout), and the local engine where the readiness check says it runs (an optional uv extra: MLX on Apple Silicon, CUDA PyTorch with an NVIDIA card, processor PyTorch without one, remembered in `.venv/.sweatcast-extra`) and the coaches' local model into `models/` (`--local` insists, `--all` fetches every local model, `--no-models` the base environment only; a profile whose `render` list leaves out local gets no engine).
- `tools/build.py` (`./sweatcast build`): draft to `.txt` and `.mp3` in one step (lint with `tools/tts_build.py`, then render with `tools/render.py`), into the draft's workout folder (else `checks/`), then a copy of the MP3 to the profile's `deliver_to` folder, after which the local MP3 is removed (the `.txt` and `.build.json` stay as history; a failed copy or no folder keeps it; the record says which, under `delivered_to`, `kept_local` and `reason`). `--web` (on by default on Claude Code on the web, where it replaces the copy) makes the web copy with `tools/webcopy.py`: the MP3 mono at 48 kbps in parts of at most 14 MB (`<name>.web-1.mp3`...) and `<name>.player.html`, a player that plays them in order, which the workout skill publishes as an artifact and the backup commits to the private repo. The lint needs the draft's menu (`<stem>.menu.json`, from `./sweatcast brief --save`) and stops on a movement that isn't on it, whatever `--force` says; only the smoke test builds without one. `--lint-only` stops after the lint; `--follow` renders ahead while a draft is still being written, keeping the model loaded and rendering each new or edited paragraph as it lands, and steps aside when the full build starts; `--clips-only` renders what the draft holds once (both local only: refused on a cloud route, where each re-render is billed); only one render runs at a time, and a second waits for the first; `--coach` names the coach (`--voice` is the old name; default the one used last) and `--engine` the route (default the first in the profile's `render` list that works here); the build resolves both and passes them to the lint and the render. `--allow-estimated` renders with a coach not yet measured on the route. Exit codes are defined in `tools/cli.py`: 2 means the total ran more than three percent off plan, 3 means the coach hasn't been measured on the route yet, 4 means a cloud service refused the key, payment or quota, 64 means the command itself was wrong.
- `tools/context.py`: the one reader and writer of the context files (profile, health, log, and private movements): the schema check, the profile's settings (`./sweatcast get coach | route | routes | wpm | experience`, `./sweatcast deliver`), coaches' `persona.md` files, `./sweatcast log-session` to add a checked session line (with `--draft`, its movements are the draft's `movements:` line, by catalog name), and `./sweatcast check`, which lists any line still showing the template's `[hint]`, any feed not filled in, a missing experience level or `[[limits]]` row, no coach yet or a coach missing a clip or still showing a hint, a route the profile names that isn't one, a fault in `me/movements.toml`, and anything the tools can't read. `tools/migrate.py` (`./sweatcast migrate`) brings an older context folder up to the current schema, backing it up first (never `.env`); 4 to 5 moves the workouts into a folder each (and `checks/`, `research/daily/`), never overwriting; 3 to 4 turns the profile's `[[voices]]` into coaches (Chatterbox Coach becomes Coach Julius and Qwen3 Coach becomes Coach Solo, old names kept as aliases), moving each voice's pace into its coach and the Narrator lines into how they talk, with cached clips still valid.
- `tools/locks.py`: the exclusive file lock the render lock and the pace file share, with flock on a Mac and msvcrt on Windows.
- `tools/draft.py`: the draft format (the `movements:` header line, never spoken, then `@@` markers, `[pause]`, `[chime]`, `[hold]`), where a draft's brief and menu sit beside it, and the timing layout the lint and the render share. `tools/tts_build.py` is the lint and `.txt` export: it stops on what must hold (text a voice can read cleanly, paragraphs short enough for one clip, the total within three percent, and the menu check), and only shows segments far off their slots (`--strict` makes those count) and each held segment's spare silence; how a script should sound is guidance in `knowledge/tts-rules.md`, `tools/render.py` the renderer (clip cache, loudness, the one-at-a-time lock, a record of each build). `tools/engines.py`: the voice engines and the voice designer, and everything that depends on mlx-audio's or huggingface_hub's internals. `tools/cli.py`: the exit codes and the argument parser every tool uses. `tools/cache.py` (`./sweatcast cache`): the clip cache's size, and `prune` for clips no build has used in a while.
- `tools/personas.py`: the coaches: lookup by folder name, name or alias, the one used last (from the log), and `voice_for(coach, route)`, the voice dict the lint, the render and the engines take. `tools/coaches.py` (`./sweatcast coaches`, `voices` its old name): list, `last`, `measured`, `design` (takes from the local Qwen3 VoiceDesign on a Mac, Fish Audio or ElevenLabs), `keep` (a take or a brought clip, converted to 24 kHz mono), `set`, `samples deepgram`, `download`. `tools/voices.py`: the local models' pins (`LOCAL_MODELS`, `ENGINE_EXTRAS`, `VOICE_DESIGN`), pace and render speed per coach, and downloads. `tools/char_weight.py` is OmniVoice's character-weight rule (Apache 2.0), vendored; every measured pace is counted in it.
- `tools/routes.py`: the routes (local, fish, elevenlabs, cartesia, deepgram), which work on this computer (the readiness check's verdict and the installed engine; a key in `me/.env`; Deepgram's stock voice) and which a build picks from the profile's `render` list. `tools/keys.py` (`./sweatcast keys`): which services have a key (never the key), and `init`. `tools/cloud.py`: the cloud engines' core (`knowledge/services.toml`, HTTP with retries, errors sorted into what the listener must fix, WAV and resampling without numpy, the cost estimate, the clone-once voice IDs), with one module per service in `tools/services/` (Fish Audio's speech and design, ElevenLabs' clone, speech with neighbors and design, Cartesia's clone and speech, Deepgram's stock voices); `tools/msgpack_min.py` is the MessagePack codec Fish needs. `tools/models.py` (`./sweatcast models`): the models in `models/`, and `adopt` from Hugging Face's usual cache.
- `tools/catalog.py`: loads and checks the movement catalog (plus any private movements), matches a logged name to a movement, forgiving plurals and a leading side word, and selects the movements a kit, level and set of limits allow. `tools/movements.py` (`./sweatcast movements`): the filter; prints the movements a kit allows (`--preset` or `--equipment`, optional `--level` and `--pattern`), minus any `--avoid` movement ids or flags, by primary pattern; `--about <ids>` prints a movement's coaching notes (setup, cues, what one rep is, where to feel it, common faults, easier and harder).
- `tools/brief.py` (`./sweatcast brief --goal --minutes --kit|--preset|--equipment`, optional `--level`, `--target`, `--limit area=level[:side]`, `--avoid`, `--save <draft path>`, `--today`): today's ingredients, in Markdown: the listener (name, level, likes and dislikes, the profile's Narrator and Default session lines), how today fits the week (from the log), today's limits (what each means, the clinician's rules, the limit cues with the side filled in, the playbook's paragraph per area, the red flags), the safe menu (every movement the kit, level, limits, `Avoid:` lines and dislikes allow, by primary pattern, healthy-side-only ones marked, each with its facts, its load on today's limited areas and its coaching notes), the weights on hand, the programming guide (the level's doses, the sprint rest rule, the time shares, the formats that fit, programming.md's rules) and the kit's notes from kits.md. It plans nothing; `--save` writes `<stem>.brief.md` and `<stem>.menu.json` beside the draft. `tools/menu.py`: the menu file and the build's check (a declared movement off the menu, a catalog movement named in the text that's off it, nothing declared, segments that don't add up to the request; a menu movement named but not declared is a warning).
- `tools/sessions.py`: loads and checks `knowledge/sessions.toml` (the methods, time shares and doses the brief's programming guide prints). `tools/screen.py`: the safety screen behind the brief's menu: it checks the request, applies the limits, the clinician's `Avoid:` lines and the dislikes, and gives the limit cues and the equipment that would open up more movements. The old composer (`./sweatcast session`) was retired in 7.2.0; the eval runs it from the v7.1.0 tag as its baseline.
- `tools/coverage.py` (`./sweatcast coverage`): reads `me/log.md` and lists the movement patterns the last session left out and those the last seven days neglected, the movements to avoid, the last format and each movement's last load, for the plan, and the days since the last session, the sessions this week and the latest feedback, for the script's continuity lines.
- `tools/feeds.py` (`./sweatcast feeds`): fetches the profile's `[[feeds]]` (team results and schedules, weather, local, science and taste headlines, weekly podcasts and puzzles, on this day, and Wikipedia's featured article, most read, in the news and did you know) into `me/workouts/research/<date>-feeds.md`, which research reads before it searches, and prints only the weather.
- `tools/content.py` (`./sweatcast content`): `plan --minutes N` prints what a session's rests carry (each slot's count and the categories due, the one told longest ago first, from the profile's `[[interests]]`), everything told in the last thirty days, the pantry's unused pieces and what to restock; `log` records the items a session told (one `--item "slot | category | title [| source [| pantry slug]]"` each); `pantry` lists the unused pieces. The research templates the workout skill fills in are in `.claude/skills/workout/research.md`.
- `tools/youtube.py` (`./sweatcast youtube`): lists recent unused videos from the profile's YouTube favorites and any series in progress, saves a video's transcript, and marks a series part as told, for the deep dive every other session; `puzzles` lists recent puzzle videos for the quiz not yet used, stocked or told.
- `tools/backup.py` (`./sweatcast backup`, optional `-m <message>`, `--no-push`): commits everything in the context folder and pushes it, when the folder is the top of its own git repo; otherwise it prints how to make one and changes nothing. It refuses a remote GitHub reports as public (asking `gh`, else GitHub's API unauthenticated). The workout skill runs it last.
- `tools/paths.py`: where everything lives (the engine, and the context folder from `SWEATCAST_HOME`, else `me/`, else on Claude Code on the web the one folder beside the engine holding a profile and `personas/`, the listener's attached private repo). `tools/workouts.py`: the folder-per-workout layout (`out_dir` for a build, and `reorganize`, which `./sweatcast migrate` runs at schema 4 to 5).
- `tools/hooks/`: the pre-push hook, `check-private.sh` (which checks every commit in a range, as the hook and CI both use it) and `private-paths`, the one list of paths that must never be pushed.
- `tests/`: fast checks for the lint, the folder-per-workout layout and its migration (`tests/test_migrate5.py`), the web copy (`tests/test_webcopy.py`), Claude Code on the web (`tests/test_setup.py`'s CloudSession), the timing layout, coaches, their design and pace (`tests/test_personas.py`), routes and keys (`tests/test_routes.py`, `tests/test_keys.py`), the cloud engines against local fake servers (`tests/test_cloud.py`, `tests/fakes.py`), the 3 to 4 migration (`tests/test_migrate4.py`, from an invented v8 folder), `models/` (`tests/test_models.py`), setup and the readiness check on faked computers (`tests/test_setup.py`), the context files and migration, the log, the movement catalog and its filter (`tests/test_catalog.py`, with a small catalog in `tests/fixtures/movements.toml`), the filler plan, record and pantry (`tests/test_content.py`), the session methods (`tests/test_sessions.py`) and the safety screen (`tests/test_screen.py`), the brief, the menu check and the draft's `movements:` line (`tests/test_brief.py`), the feed parsers, the YouTube series, the backup (`tests/test_backup.py`, with local repos only), `./sweatcast` and the build's exit codes, the privacy hook, and a fresh copy running on `me.example/`, with no models, network or personal files (fixtures in `tests/fixtures/`). Run `./sweatcast test` after changing a tool; CI runs them on every push with Python 3.11.
- `pyproject.toml`, `uv.lock`, `.python-version`: the pinned Python environment.
- `docs/research/`: the session-structure research `knowledge/sessions.toml` cites.
- `docs/eval/`: the judged eval grid behind each release's session quality: the cases (`cases.toml`, and `extra-cases.toml` beyond the forty), the invented listeners, `briefs.sh` (each case's brief and menu) and `skeletons.sh` (the composer's baseline), the writer's and the judge's briefs, and a results file per run.
- `VERSION`, `CHANGELOG.md`: the release number and what changed in each release.

## Audio
`tools/render.py` voices each paragraph in the coach's voice by cloning their clip, on the route the build picked: locally with Chatterbox Turbo or Qwen3-TTS through `mlx-audio` on an Apple Silicon Mac, or Chatterbox Turbo through Resemble AI's PyTorch `chatterbox-tts` on Windows or Linux (CUDA with an NVIDIA card; the processor without one, experimental and untimed); or by a cloud service with the listener's key (Fish Audio, ElevenLabs, Cartesia, Deepgram; `tools/cloud.py`). Every engine returns `say(text, seed)` with 16-bit mono PCM at 24 kHz, so the clip cache, loudness pass, timing layout and build record don't know which spoke; the cache key holds the clip, engine, model, settings and runtime, never a key or a name. The local engines load in `tools/engines.py`, in the project's own environment (`.venv`, Python 3.11, pinned by `uv.lock` for Mac, Windows and Linux; the local engine is an optional extra). On Windows, `./sweatcast` runs from Git Bash and the venv's Python is `.venv/Scripts/python.exe`; Qwen3 and local voice design are Mac-only. Every tool runs through `./sweatcast`, or under `SWEATCAST_PYTHON` if set; the Mac's own `python3` is never used. On an M3 with 16 GB, Chatterbox Turbo renders at about 0.7 times the length of the speech and Qwen3 at about 1.3 to 1.45 (on an RTX 2080 Super, Chatterbox Turbo at about 0.5), so a 30-minute workout takes under 20 minutes. Turbo's decoding keeps the GPU busy, so a local render (or a voice design) holds a lock and a second one waits; rendering ahead with `--follow` while the draft is written is the way to overlap work locally. A cloud build sends only once, at the end, a few requests at a time, after printing the characters and approximate cost and checking the profile's `cloud_max_chars`. Local model weights live in `models/` (about 3.3 GB for Chatterbox Turbo, 4.2 GB for Qwen3, 4.5 GB for the voice designer; 4 GB for Chatterbox Turbo on PyTorch), downloaded at pinned revisions; keep only the ones a coach in use needs. A coach is a reference clip, not a tuned model (`knowledge/voices.md`). On Claude Code on the web only the cloud routes run: the key is an environment variable in the cloud environment's settings (the tools read the environment before `me/.env`), and the service's host goes on its network allowlist.

## Releases
Versions follow Semantic Versioning, tracked in `VERSION` (and `pyproject.toml`) and `CHANGELOG.md`, and tagged `vX.Y.Z` on GitHub (RNCDev/sweatcast).
- Major: a change that breaks how existing drafts, coaches, commands or the `me/` layout work, so something has to be migrated. Its CHANGELOG section says how, under "For forks". A change to a context file's format raises `SCHEMA` in `tools/context.py` and adds a step to `tools/migrate.py`, so a fork migrates with one command (`./sweatcast migrate`, which `./sweatcast setup` also runs).
- Minor: a new capability, such as an engine, a cloud service, a skill step or a tool option.
- Patch: fixes, tuning and doc corrections.

Listener content (sessions, research sheets, log entries) lives in `me/` and is never part of the engine's git. When a set of tool, skill or doc changes is finished and working, release it: add a dated section to `CHANGELOG.md`, bump `VERSION` and `pyproject.toml`, commit, tag (`git tag -a vX.Y.Z -m "..."`), push with tags, and publish a GitHub release (`gh release create vX.Y.Z --notes-file <that changelog section>`). Ask before pushing if it's unclear whether the work is done.
