# Setup: a new listener's context

Goal: in one short conversation, turn `me.example/` into a filled-in `me/` folder, check the machine, and end with a short first workout as an end-to-end test. Everything personal goes in `me/` (git-ignored); never edit the engine (tools, skills, `knowledge/`) for one listener.

The listener may be a stranger who has read nothing: explain each step in a line, in plain words, and never send them to the README.

## Step 0: what this computer can do

Run `./sweatcast doctor` first and relay what matters in two or three plain lines: the computer, whether local voices work here, and anything missing.
- **A Claude Code cloud session** (doctor's report starts with "This is a Claude Code cloud session"): relay its lines and stop. Set nothing up.
- **uv missing:** ask once (AskUserQuestion) whether to install it with Astral's official installer, which needs no admin rights; it runs a downloaded script, so ask first. On yes, `./sweatcast setup --install-uv --no-models` (it installs uv, then carries on as in Step 1).
- **No local voices here** (an Intel Mac, or below the memory or disk floor): say so now, before the interview, with doctor's reason. Audio then comes from a cloud voice with the listener's own key (Step 2, Audio). **The processor only** (Windows or Linux without an NVIDIA card): local voices work but are experimental, speed unknown and likely slow; offer a cloud voice too.
- ffmpeg isn't a prerequisite: the Python environment brings its own. git isn't either: outside a git checkout (a zip download), setup skips only the privacy hook.

## Step 1: the machine

Run `./sweatcast setup --no-models`. It makes the Python environment with uv, copies `me.example/` to `me/` if there's no `me/profile.md` yet (or brings an existing one up to this version's format, backing it up first), and installs the git hook that refuses to push `me/` in any commit. The local engine and its model come later, once the audio route is settled, so nothing large downloads for a route they won't use. If it stops, relay its one-line fix and rerun it once they say it's done. It runs in the background while you interview: start it with `run_in_background: true`.

If `me/profile.md` already has real answers, this is an update: ask only about what the user wants to change, and skip to Step 3.

## Step 2: the interview (AskUserQuestion, at most three rounds of up to four questions)

Read `me.example/profile.md` and `me.example/health.md` first, so the questions match the files. Ask in this order, offering sensible options and leaving the rest to Other:

1. **Basics.** The name or nickname the coach should call them (it goes in the settings as `name`, and the coach greets them by it), neighborhood and city (only for local news and weather), current goals, and **experience level**, three choices in the listener's own words: novice (new to training, or back after a long break; simple movements, lighter loads), experienced (trains regularly and knows the common lifts), advanced (trains hard and wants harder variations). It becomes `experience` in the profile's settings.
2. **Equipment kits.** What's at home, and when travelling or at a gym. Each kit becomes one `[[kits]]` row in the profile's settings: a `name` and the `equipment` ids it holds, from the catalog's equipment list (the `equipment` list near the top of `knowledge/movements.toml`; the `[presets.*]` tables in that file are kit presets to start from). The first kit is the default. For free weights, also ask which weights are there and write them as `weights` (equipment id = the weights, lightest to heaviest) with `unit` (`"lb"` or `"kg"`), for example `weights = { dumbbells = [10, 15, 20], kettlebell = [30] }`, so the brief prints what's on hand and the session prescribes only those. Also copy each kit into the prose under Equipment kits.
3. **Likes and dislikes.** Movements they enjoy or want left out. Resolve each name against the catalog (`./sweatcast movements --equipment <ids>` prints movement names, which the catalog resolves to ids) and put the ids in `likes` and `dislikes`; a name the catalog doesn't know goes in the profile's prose, not in the list.
4. **Health.** Any current injuries or limitations, what a clinician said about them, and how it feels today. Say plainly, once: sweatcast isn't medical advice, a clinician's instructions override everything, and red flags (can't bear weight, rapidly increasing swelling, numbness, giving way, getting worse after a week or two) mean seeing a clinician before training. Walk each injury into one `[[limits]]` row in the settings block of `me/health.md` (the template, `me.example/health.md`, shows one):
   - `area`, from the catalog's list of thirteen: foot, ankle, calf, knee, hamstring, hip, groin, low-back, rib, shoulder, elbow, wrist, neck. Spell it as written here, with the hyphen in low-back.
   - `side`: left, right or both.
   - `level`: off-limits means nothing that loads the area at all; delicate means nothing that loads it hard, no impact and no fast work. Offer both in those words and let the clinician's words decide; when unsure, off-limits.
   - `note`: the clinician's words, short. Put them word for word under `## Clinician rules` too; each is followed literally. An injury in none of the thirteen areas gets no row: write it in the prose list as "- Unlisted: <what>", and put any movement ids or flags to avoid for it under `## Clinician rules` as a line "Avoid: <ids or flags>" (ids from the catalog, flags from its `flags` list), which `./sweatcast brief` applies on every run. The playbook's "Unlisted injuries" says what to do.
   - `rehab` and `flags` stay empty unless the clinician named a rehab movement or something else to avoid; `flags` values come from the catalog's fixed `flags` list.
   Add the injury and its programming to the prose list under Active injuries too (an unlisted one as "- Unlisted: <what>", as above). No injuries: leave "None right now." and no rows.
5. **Interests and taste.** Teams, topics, YouTube channels for deep dives, puzzles, books, local news, and anything never to bring up; then favorite shows, books, music, comedians, restaurants and drinks, with ratings if they have them. Interests become `[[interests]]` rows in the profile's settings (name, slot from `knowledge/content.toml`, detail); favorites go under `## Taste`; and find a feed for each taste area that has one.
6. **Audio.** How the workouts become audio. Offer what doctor's Audio routes section says works here:
   - **Local** (where it works): free, private, on this computer; the engine and model are a 3 to 4 GB download, and Apple Silicon renders a 30-minute workout in about 20 minutes. On the processor, say it's experimental and slow.
   - **A cloud voice with their own key:** Fish Audio (about $0.30 a workout, the cheapest; it copies the coach's clip on every request), ElevenLabs (about $0.80 with Flash, $1.60 with the more natural multilingual model; suggest the natural one), Cartesia (about $1.00; a paid plan for cloning) or Deepgram (about $0.60; stock voices only, so the coach sounds different there). ElevenLabs, Cartesia and Deepgram are "not yet tried live": say so.
   - For a cloud voice, say once, plainly: the script goes to the service and can mention their injuries ("easy on that left knee"); roughly what a workout costs there (approximate; prices change); and the key is stored in `me/.env` on this computer only, never backed up or shown, and removed by deleting its line. Then `./sweatcast keys init <service>`, give them the file's path (a clickable link in an IDE) and ask them to paste the key after the `=` and save. Never ask for the key in the chat, and never open, print or copy `me/.env`. `./sweatcast keys` confirms it's set.
   - The choice is the profile's `render` list, in order of preference, such as `["local", "fish"]` (each build takes the first that works on the computer it runs on). Enabling a cloud voice also writes `cloud_max_chars = 30000` (a 40-minute workout with room for retakes, about $0.45 on Fish, $2.40 on ElevenLabs multilingual): tell them the figure and that a build over it stops before sending.
7. **Delivery.** Where finished MP3s should go: a folder that syncs to their phone (iCloud Drive is `~/Library/Mobile Documents/com~apple~CloudDocs/<folder>`, Google Drive for desktop is `~/Library/CloudStorage/GoogleDrive-*/My Drive/<folder>` on a Mac and usually `G:/My Drive/<folder>` on Windows (forward slashes), Dropbox is `~/Library/CloudStorage/Dropbox/<folder>`), or nowhere, keeping them only in `me/workouts/`. Say that once a build's copy lands there, the local MP3 is removed and only the script's text stays in `me/workouts/`, so this folder is where the audio lives. Check the folder exists with `ls`, and offer to create the subfolder. It is the profile's `deliver_to` setting, a folder or a list of them, one per computer the listener renders on (each build copies to the ones that exist there); a request to change where workouts go runs this step alone.

## Step 3: write the files

- `me/profile.md` and `me/health.md`: fill in every bracketed placeholder from the answers (the template is `me.example/`), and delete lines the user has nothing for. Keep the `+++` block at the top of each file. In `me/profile.md` that block is TOML and holds every setting the tools read: `name`, `experience`, `likes`, `dislikes`, `deliver_to`, `words_per_minute`, `youtube_favorites` and `puzzles` (@handles without the @), `render` (the audio routes, in order) and, with a cloud voice, `cloud_max_chars`, one `[[kits]]` table per kit (`name`, `equipment`, and for free weights `weights` and `unit`), and one `[[feeds]]` table per feed (`label`, `kind`, `value`). Edit those values in place; the prose below the block is for Claude only. Writing `me/health.md` asks the user for permission; that's expected, since it's the most private file.
- **Feeds.** Weather: the neighborhood's latitude and longitude, rounded to two decimals. Teams: find each team's ESPN path (the `sport/league/team` part of its ESPN team page URL, such as `hockey/nhl/nj` or `soccer/usa.1/10739`) with a web search. Local news: one or two outlets' RSS feeds for the city. Keep the shipped science and puzzle feeds unless the user doesn't want them. YouTube handles: check each one resolves (`https://www.youtube.com/@<handle>`).
- Then run `./sweatcast check`. It lists every line still showing the template's `[hint]`, any feed not filled in, a missing experience level, likes or dislikes the catalog doesn't know, kit equipment not in the catalog, a malformed `[[limits]]` row (which would apply no limit at all), an unknown rehab id or one that isn't a rehab movement, a bad `flags` value, an injury written in prose with no `[[limits]]` row, and anything the tools can't read, with line numbers; fix or delete each until it reports no issues (its notes, such as no delivery folder or an unknown like, are fine). Run `./sweatcast feeds` once, fix or remove any source it lists under "Couldn't fetch", and run it again.

## Step 4: first audio

1. **The local engine,** when the route includes local: if doctor (or `./sweatcast models adopt --dry-run`) found sweatcast's models already downloaded elsewhere, offer to move them (`./sweatcast models adopt`) rather than download again. Say the size (3.3 GB for Chatterbox Turbo on a Mac, 4 GB on Windows or Linux, plus the engine itself), then run `./sweatcast setup --local` with `run_in_background: true`. It skips what's done. Finish Step 3's feeds while it runs.
2. **The coach,** which setup can't finish without: run the `coach` skill. Its designer depends on the route (local design on an Apple Silicon Mac, else Fish Audio or ElevenLabs with the key, else a clip they bring), so it comes after the route and key.
3. **The smoke test** with the new coach on this computer's route: `./sweatcast build knowledge/smoke-test.draft.txt "smoke-test" --coach "<coach>"`. It measures the coach's pace, which session builds require (and on the processor, this computer's render speed: `./sweatcast doctor` then quotes the time a 30-minute workout takes; past an hour, suggest a cloud voice and let them choose). Send `me/workouts/smoke-test.mp3` with SendUserFile if it's available, and ask how it sounds.
4. Offer a ten-minute first session (the `workout` skill, strength at ten minutes) as the end-to-end check, including the copy to the delivery folder.

## Step 5: keep it safe

- Suggest backing up `me/` as its own private git repo: `git init` inside `me/`, commit, and push to a private remote. The engine's git ignores `me/`, so the two never mix, and the pre-push hook blocks `me/` from the public repo.
- Summarize what was written, in a few lines, and where to change it later ("ask me to update your profile").
